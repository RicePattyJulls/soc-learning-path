
Telemetría → detecciones automáticas nativas + detecciones creadas por ti (Custom Detection / Analytics Rules) → alertas → correlación automática (Defender XDR / Fusion en Sentinel) → incidente → respuesta → remediación

Y dentro de respuesta/remediación puedes meter:

- AIR → parte de alertas.
- Automatic Attack Disruption → actúa sobre ataques/incidentes de alta confianza.
- ZAP → remediación automática de correo.
- SOAR → Automation Rules + Playbooks.
- Acciones manuales → aislar dispositivo, deshabilitar usuario, eliminar correo, etc.

___

```
1️⃣ Detección → alerta → respuesta directa  
│  
└──▶ Telemetría/logs → Custom Detection / Analytics Rule (adicionales) → KQL evalúa condición → match → identifica entidades (Entity Mapping en Analytics Rule) → alerta → correlación automática → incidente → respuesta  
   ├──▶ Defender XDR nativo → Custom Detection actions / AIR (MDE & MDO) → remediación  
   └──▶ Sentinel SOAR → Automation Rule → Playbook → enriquecimiento / notificación / contención / remediación
   
2️⃣ Alertas → incidente → respuesta  
│  
└──▶ Alertas → motor de correlación de Defender XDR | Fusion si Sentinel no está incorporado → correlación → incidente  
   ├──▶ Defender XDR → Automatic Attack Disruption → contención automática → remediación posterior por SOC  
   └──▶ Sentinel SOAR → Automation Rule → Playbook → enriquecimiento / notificación / contención / remediación
```

> Las remediaciones nativas de Defender XDR terminan registradas en Action Center. Las acciones de Sentinel/Playbooks no necesariamente aparecen ahí.

# 1 · Licencia y onboarding

- `Licenciamiento`: derecho de uso que habilita capacidades y determina qué nivel del producto está cubierto. No conecta ni ingiere datos. No todo exige una licencia premium: Entra Free conserva funciones básicas, Purview Audit Standard se incluye en suscripciones compatibles y Microsoft Defender Antivirus forma parte de Windows.
- `Onboarding`: incorporación técnica de un tenant, workspace, suscripción, recurso, aplicación, dispositivo o sensor al producto. Solo aplica donde existe ese paso: servicios cloud como Entra ID y la protección base de correo generan datos nativamente, mientras que MDE, los sensores de MDI, Endpoint DLP, los planes de Defender for Cloud y Sentinel sí requieren activación o incorporación.

Si el tenant pasa de `E5` a `E3`, `Microsoft Defender for Office 365` baja de Plan 2 a Plan 1 —incluido en E3 desde el 1 de julio de 2026— y se pierden capacidades P2 como `Threat Explorer`, `Attack simulation training` y AIR de MDO; MDI, MDCA y Entra ID Protection P2 dejan de estar cubiertos salvo otra licencia equivalente. Los datos ya ingeridos en un Log Analytics workspace siguen su propia retención; tras finalizar la gracia, es razonable inferir —Learn no lo afirma en estos términos— que deja de generarse telemetría propia de las capacidades perdidas, ya que el servicio que la produce ya no está licenciado.

Arquitectura de workspaces

| Arquitectura | Cuándo | A cambio |
| --- | --- | --- |
| Un solo workspace en un tenant | Es la opción normal cuando no hay razón para separar el dato: todo se consulta junto | El log viaja entre regiones y puede generar coste de ancho de banda; no sirve si la gobernanza obliga a mantener el dato en una región |
| Un workspace por región en un tenant | Hay requisitos de residencia del dato, o interesan retención, acceso y facturación granulares por región | Hay que desplegar analíticas y workbooks en cada workspace, y la correlación de incidentes sigue siendo por workspace |
| Varios tenants | Se administran workspaces que no están en el propio tenant, el caso típico de un MSSP | En el portal de Azure, `Azure Lighthouse` permite administrar recursos delegados de clientes sin trasladar su propiedad ni centralizar los datos. En el portal de `Microsoft Defender`, el acceso multitenant a datos de `Microsoft Sentinel` utiliza `Microsoft Entra Business-to-Business (B2B)`; `granular delegated admin privileges (GDAP)` con `Azure Lighthouse` no está soportado para esos datos. Dentro de cada `tenant` se decide si separar `workspaces` por región |

Cada tenant necesita al menos su propio workspace, porque los conectores de servicios Microsoft están acotados al tenant. La región se elige al crear el `Log Analytics workspace` y no se puede cambiar: para moverlo hay que recrearlo, y el nombre del workspace es también el nombre de Sentinel. Un workspace creado a mano puede compartirse entre Microsoft Sentinel y Microsoft Defender for Cloud, pero los workspaces que Defender for Cloud crea por defecto no aparecen al habilitar Sentinel. # 2 · Permisos y RBAC

> La licencia habilita el servicio; el permiso autoriza a una identidad para verlo, configurarlo o actuar. Son ejes independientes: una licencia no concede privilegios y un rol no sustituye los requisitos de licencia del producto.
## 1 · Modelos y scopes

No existe un único RBAC para toda la plataforma:

| Modelo                                       | Qué gobierna                                                                                                                        |
| -------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `Unified RBAC`                               | Experiencias y acciones dentro de `security.microsoft.com`, acotadas mediante `Data sources`, `Data collections` y Sentinel scopes  |
| `Azure RBAC`                                 | Microsoft Sentinel SIEM, el `Log Analytics workspace` y recursos de Azure como `Data Collection Rule (DCR)`, workbooks y Logic Apps |
| Entra ID RBAC / roles del Sentinel Data Lake | Acceso amplio al Tenant Data Lake y operaciones de incorporación que afectan al tenant                                              |
| Purview + Email & collaboration role groups  | Audit, eDiscovery, DLP, Insider Risk Management y determinadas acciones sobre correo                                                |
Los permisos son acumulativos. Una asignación amplia de Azure o Entra puede imponerse al alcance más estrecho de otra asignación; por eso el diseño parte de mínimo privilegio y del scope más pequeño que permita la tarea.

## 2 · Azure RBAC para Microsoft Sentinel

Microsoft recomienda asignar los roles de Sentinel al resource group que contiene el workspace. Así alcanzan el workspace, el recurso `SecurityInsights` y los recursos relacionados. Si se asignan solo al workspace, hay que mantener por separado los permisos sobre `SecurityInsights`, playbooks y demás recursos externos.

```
Resource Group (recomendado: asignar roles acá)
  │
  ├──▶ Log Analytics Workspace
  │
  ├──▶ SecurityInsights (solution resource)
  │
  ├──▶ Analytics rules              → Microsoft Sentinel Contributor
  │
  ├──▶ Logic Apps / Playbooks       → Logic App Contributor (crear/editar) + Microsoft Sentinel Playbook Operator (correr/adjuntar)
  │
  ├──▶ Workbooks                    → Workbook Contributor o Microsoft Sentinel Contributor (o rol Sentinel menor)
  │
  └──▶ otros recursos externos, ej.:
         ├── Data connectors específicos (Event Hub, Key Vault, Storage Account…)
         │      → Microsoft Sentinel Contributor (nivel de RG) + rol propio del conector (según su doc)
         │
         ├── Cuenta de SERVICIO de Sentinel para automation rules → playbook
         │      → Microsoft Sentinel Automation Contributor
         │
         └── Guest users que asignan incidentes
                → Directory Reader (Entra ID) + Microsoft Sentinel Responder (mínimo documentado)
```
### Roles de Microsoft Sentinel

Controla el servicio Microsoft Sentinel: incidentes, analytics rules, hunting, automation, Content Hub, etc.

| Rol                                         | Qué permite                                                                                                                                                                                                                                                                                                      |
| ------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Microsoft Sentinel Reader`                 | Ver datos, incidentes, workbooks, recomendaciones y otros recursos, hunting query                                                                                                                                                                                                                                |
| `Microsoft Sentinel Responder`              | Todo Reader, más administrar incidentes                                                                                                                                                                                                                                                                          |

### Alcance y Sentinel scoping

- Data sources = qué productos/workloads de Defender puede ver.
- Data collections = qué workspaces o Data Lake puede consultar.
- `Include future data sources automatically` = si mañana añades una nueva fuente, entra automáticamente en el alcance.
- Sentinel scoping = limitar qué filas puede ver un usuario dentro del mismo workspace.
	- Ejemplo: mismo workspace, pero un scope puede hacer que un analista vea solo datos de `Finance`, mientras otro ve solo `HR`.
- Ese scoping se aplica al ingerir datos nuevos; lo viejo no se etiqueta retroactivamente.
- Para configurar scopes necesitas `Authorization (Manage)`; para tablas/reglas relacionadas, `Data (Manage)` y `Alerts (Manage)`.
- Crear la `DCR` requiere `Owner` o `Microsoft.Insights/DataCollectionRules/Write`.
- Los scopes se acumulan, solo funcionan en tablas compatibles con transformación en ingesta y no aplican a tablas nativas de XDR.
- Si una experiencia no soporta row-level RBAC, como ciertos notebooks del Data Lake, el usuario scoped no verá esos datos ahí.

## Microsoft Defender for Endpoint (MDE)

En `Microsoft Defender for Endpoint`, esta capa reúne los controles que aplican una decisión sobre la actividad y las capacidades que evalúan la postura del dispositivo. Un control en `Audit` solo registra lo que habría impedido; en `Block` aplica la protección. En ambos casos deja telemetría, y un intento bloqueado también puede generar una alerta.

Excluir una IP detiene el escaneo activo, pero el dispositivo aún puede descubrirse de forma pasiva o por multicast. `Basic discovery` solo observa el tráfico pasivamente y ve menos. 
### Device groups

> `security.microsoft.com > Settings > Endpoints > Permissions > Device groups > Add device group`. Existen en `Plan 1` y en `Plan 2`, y el límite es de 2.000 device groups por tenant.

Device group: agrupación lógica de dispositivos que permite administrar conjuntamente su visibilidad, su remediación automática y su filtrado. La pertenencia combina nombre, dominio, etiquetas y plataforma: el dispositivo debe cumplir todas las propiedades configuradas, pero le basta uno de los valores de cada una (`OR`), y se admiten hasta 10 valores por etiqueta, nombre de dispositivo y dominio. Si un dispositivo coincide con varios grupos, entra en el de menor número (`1` tiene prioridad). Si no coincide con ninguno, va a `Ungrouped devices (default)`, que no se puede reordenar ni borrar, aunque sí admite cambiarle el nivel de remediación y quién lo ve.

- Limita qué alertas y datos ve cada grupo de usuarios de Microsoft Entra con rol RBAC asignado.
- Asigna el nivel de remediación automática de ese conjunto de dispositivos.
- Permite filtrar el inventario con el filtro `Group`.
- Permite acotar indicadores a uno o varios device groups.
- Los cambios de configuración pueden tardar de varios minutos a varias horas en propagarse.

### Rules: indicators, web content filtering y exclusiones

`Settings > Endpoints > Rules` reúne páginas distintas y no todas hacen detección:

| Página                         | Función                                                                                                                                                                                                                                                |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `Indicators`                   | Declara veredictos propios para hashes, direcciones IP, direcciones URL, dominios y certificados                                                                                                                                                       |
| `Web content filtering`        | Define las categorías de contenido web bloqueadas                                                                                                                                                                                                      |
| `Automation uploads`           | Enciende `Content analysis` y declara las extensiones de fichero y de adjunto que se suben a la nube para inspeccionarlas durante una investigación automatizada. Su retención está en `# 5 · Almacenamiento y Retención > 2 · Microsoft Defender XDR` |
| `Automation folder exclusions` | Define carpetas que AIR no examina ni remedia; no las excluye de los análisis antivirus                                                                                                                                                                |
| `Custom Data Collection`       | Recoge eventos adicionales del endpoint hacia Sentinel; configuración y requisitos en `# 4 · Ingesta > Configuración clave > Custom Data Collection de MDE`                                                                                            |

Una entrada de `Automation folder exclusions` exige `Folder`, que incluye sus subcarpetas y admite comodín final, y una descripción; `Extensions` y `File names` son opcionales y acotan dentro de esa carpeta. Para dejar fuera solo `C:\myapp\myapp.exe` se pone `C:\myapp` como carpeta y `myapp.exe` en `File names`. Aplica a todos los dispositivos incorporados, `Live response` tampoco puede recopilar ni examinar lo excluido y devuelve `File is excluded`, y el antivirus sigue analizándolo.

`Alert suppression` pertenece a `Detección y alertas`; no es un control de protección. Fuente: [Automation folder exclusions](https://learn.microsoft.com/en-us/defender-endpoint/automation-folder-exclusions-configure).

Indicadores, `Indicators`, es lo que más cae. Se crean sobre cuatro tipos de entidad y no todos admiten las mismas acciones:

| Tipo de indicador | Acciones disponibles                                               |
| ----------------- | ------------------------------------------------------------------ |
| Ficheros          | `Allow`, `Audit`, `Warn`, `Block execution`, `Block and remediate` |
| Direcciones `IP`  | `Allow`, `Audit`, `Warn`, `Block execution`                        |
| `URL` y dominios  | `Allow`, `Audit`, `Warn`, `Block execution`                        |
| Certificados      | `Allow`, `Block and remediate`                                     |

- Límite: 15.000 indicadores por tenant; no ampliable.
- Motores: detección en la nube, `Microsoft Defender Antivirus` y Automated Investigation and Response (`AIR`).
- Importación: máximo 500 indicadores por lote.
- Tipos por importación CSV: `FileSha1`, `FileSha256`, `IpAddress`, `DomainName` y `Url`. La API añade además `FileMd5` y `CertificateThumbprint`.
- Valores de acción: `Allowed`, `Audit`, `Warn`, `Block` y `BlockAndRemediate`; la API también expone `Alert` y `AlertAndBlock`, pero son acciones legacy, soportadas solo hasta enero de 2022 y no deben usarse hoy.
- Alertas: `Allow` no genera ninguna; `Audit` usa la severidad definida; `Block` y `Warn` generan una alerta informativa genérica, sin título ni severidad personalizados.
- IP: solo direcciones externas, nunca internas; admite `IPv4` punteado o `IPv6` con los ocho segmentos, pero no rangos, comodines ni notación `Classless Inter-Domain Routing (CIDR)`.
- Certificados: solo se evalúa el certificado hoja, no sus padres ni sus hijos, y debe encadenar a una autoridad raíz de confianza o ser autofirmado e instalado como raíz de confianza en el dispositivo. Solo admite `.CER` y `.PEM`, los firmados por Microsoft no se pueden bloquear, y crear o quitar uno tarda hasta 3 horas. Un certificado en `Block` gana a un indicador de hash en `Allow` sobre un fichero firmado por él.
- Dominios: incluyen sus subdominios; un indicador `Allow` permite exceptuar un sitio del filtrado de contenido web para un device group concreto.
- URL HTTPS: la coincidencia de rutas solo funciona en Microsoft Edge.
- Precedencia de red: `Allow > Warn > Block`.
- Precedencia de hashes: `SHA-256 > SHA-1 > MD5`.
- Warn: permite un bypass temporal y no equivale a `Block`.
- Requisitos: en `Microsoft Edge`, los indicadores de red se aplican mediante `Microsoft Defender SmartScreen`; en otros navegadores y aplicaciones requieren `Network protection` en `Block`. Los indicadores de fichero requieren `cloud-delivered protection`.
	- SmartScreen es básicamente un filtro de reputación de Microsoft: comprueba si una web, URL, app o archivo descargado es conocido como malicioso/sospechoso y puede mostrar advertencia o bloquearlo. También existe en Windows para “Check apps and files”, no solo dentro de Edge.
		- Edge → SmartScreen
		- Chrome/Firefox/PowerShell/etc. → Network Protection (Block)
		- Archivos/apps descargados en Windows → SmartScreen también puede intervenir.
- Limitaciones: los indicadores no funcionan con Defender Antivirus en modo pasivo; sus exclusiones prevalecen sobre los indicadores de fichero y certificado; los indicadores de red no admiten `Block and remediate`.
- Objetivo (target): sin verificar en Learn — el material oficial de práctica afirma que el indicador queda inactivo hasta asignarle un objetivo válido y que la acción sola no lo activa; la referencia de indicadores no lo dice así, solo documenta entidad, acción, caducidad y alcance. Lo que sí está documentado: las políticas de threat intelligence personalizadas aplican a fuentes integradas, no a indicadores individuales.
- Indicador inactivo: revisar valor, expiración, device scope y prerrequisitos de enforcement, no solo que tenga un target.

Cuando varios mecanismos opinan sobre el mismo fichero, Windows los evalúa en un orden fijo y se detiene en la primera condición que aplica, de modo que el resultado no depende de cuál se configuró antes sino de la posición en esta cadena:

| Orden | Condición                                                                              | Resultado             |
| ----- | -------------------------------------------------------------------------------------- | --------------------- |
| 1     | `App Control for Business (WDAC)` o `AppLocker` en enforce mode no permiten el fichero | Bloqueado             |
| 2     | Una exclusión de `Microsoft Defender Antivirus` permite el fichero                     | Permitido             |
| 3     | El fichero tiene un indicador `Block` o `Warn`                                         | Bloqueado o advertido |
| 4     | `Microsoft Defender SmartScreen` bloquea el fichero                                    | Bloqueado             |
| 5     | El fichero tiene un indicador `Allow`                                                  | Permitido             |
| 6     | Lo bloquea una regla `ASR`, `Controlled Folder Access (CFA)` o el propio antivirus     | Bloqueado             |
| 7     | Ninguna de las anteriores                                                              | Permitido             |

Lo que hay que leer de esta tabla es el 2 contra el 3: una exclusión de `Microsoft Defender Antivirus` se evalúa antes que un indicador `Block`, así que la exclusión gana y el indicador nunca llega a aplicarse. Es la misma limitación anotada arriba, vista desde la cadena completa. El 1 marca el otro extremo: ni una exclusión ni un indicador `Allow` rescatan un fichero que `WDAC` o `AppLocker` ya rechazaron en enforce mode. Y el 6 explica por qué una exclusión de antivirus no basta para que un binario pase: las reglas `ASR` y `CFA` se evalúan por su cuenta y solo algunas reglas `ASR` honran las exclusiones de ruta del antivirus. Fuente: [Overview of exclusions and indicators](https://learn.microsoft.com/en-us/defender-endpoint/defender-endpoint-exclusions-overview).

### Deception

### Reglas ASR

> Ciclo de despliegue de cualquier regla ASR: planificar → probar (Audit) → habilitar (Block) → mantener (revisar que siga sirviendo).

`ASR` (`Attack Surface Reduction`) = reglas que bloquean comportamientos típicos de malware/ransomware antes de que ocurra el daño (ej: macros de Office lanzando procesos, scripts ofuscados, robo de credenciales de LSASS). Es prevención pre-brecha, reduciendo la "superficie" que un atacante puede explotar — lo opuesto a EDR in block mode, que actúa post-brecha, solo es exclusivo de MDE. Las reglas `ASR` solo se evalúan en Windows si `Microsoft Defender Antivirus` es el antivirus principal, está en modo `Active` y tiene `real-time protection` habilitada. Learn añade un cuarto requisito de versión: los tres componentes de `Microsoft Defender Antivirus` no pueden quedarse más de dos versiones por detrás de la disponible, ni la `Platform update version`, ni la `MEngine version`, ni la `Security intelligence`, porque mantenerlos al día reduce los falsos positivos de las reglas `ASR` y mejora la detección del propio antivirus.

`Cloud-delivered protection` es crítica para el funcionamiento del conjunto, y tres reglas la exigen expresamente para poder usarse: `Block executable files from running unless they meet a prevalence, age, or trusted list criterion`, `Block execution of potentially obfuscated scripts` y `Use advanced protection against ransomware`.

MDE supervisa las reglas `ASR`, pero no distribuye directamente su configuración. El método recomendado son las `Endpoint security policies` de Intune o del portal de Defender; también pueden usarse `OMA-URI`, cualquier MDM mediante `Policy CSP`, `Microsoft Configuration Manager`, `Group Policy` o `PowerShell`. La excepción son las endpoint security policies de Intune, las del propio portal de Defender —que usan las mismas policies que Intune— y `Microsoft Configuration Manager`; todos los demás métodos, incluidos los perfiles personalizados de Intune con `OMA-URI`, identifican cada regla mediante su `GUID`.

| Modo               | Código | Comportamiento                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| ------------------ | ------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Off` / `Disabled` | `0`    | Deshabilita expresamente la regla y puede crear conflicto si otra política la configura de otra forma                                                                                                                                                                                                                                                                                                                                                                   |
| `Block`            | `1`    | Bloquea la actividad                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| `Audit`            | `2`    | Evalúa y registra lo que habría bloqueado, sin impedirlo                                                                                                                                                                                                                                                                                                                                                                                                                |
| `Not configured`   | `5`    | No habilita expresamente la regla y evita el conflicto que puede provocar `Disabled`                                                                                                                                                                                                                                                                                                                                                                                    |
| `Warn`             | `6`    | Bloquea, pero el usuario puede elegir `Unblock` para omitir el bloqueo durante 24 horas; desde la platform `4.18.26060`, hacerlo exige aprobación de administrador. Exige platform `4.18.2008.9` y engine `1.1.17400.5` o posteriores. No está disponible en Configuration Manager, en Windows anterior a 1809 se comporta como `Block`, y no lo admiten `Block credential stealing from LSASS` ni `Block Office applications from injecting code into other processes` |

Las reglas de si o si son 3 de las 19 reglas totales, marcadas como "standard protection rules" porque Microsoft las considera de bajísimo riesgo de falso positivo.

1. `Block abuse of exploited vulnerable signed drivers` — impide guardar drivers firmados vulnerables en el equipo; no impide cargar los que ya estaban guardados (técnica típica de "BYOVD" — traer tu propio driver vulnerable para saltarte protecciones a nivel kernel).
2. `Block credential stealing from the Windows local security authority subsystem` — bloquea el robo de credenciales de LSASS (el proceso donde Windows guarda hashes/tickets en memoria — es literalmente lo que hace mimikatz).
	- La regla de LSASS se vuelve inútil/redundante si ya tienes activados LSA protection y Credential Guard (protecciones nativas de Windows que ya hacen básicamente lo mismo). Tan redundante que el portal directamente la marca como "not applicable" — ni te deja fingir que la estás usando.
3. `Block persistence through WMI event subscription` — bloquea que un atacante use WMI para "quedarse pegado" al sistema (crear una suscripción a eventos que reactive su malware cada vez que pasa algo, tipo reinicio).

> si una regla está en modo Audit en vez de Block, o si el equipo tiene exclusiones mal configuradas para "que no rompa X app", eso es tan válido como buscar un PoC — es la primera pregunta real en una auditoría antes de intentar nada técnico.

Para una auditoría real (no CTF), el orden correcto sería:

1. Enumerar qué reglas ASR están realmente en Block vs Audit vs Not configured (esto lo ves con `Get-MpPreference` o en el portal si tienes acceso).
2. Revisar exclusiones — muchas veces ahí está el hueco, no en un bypass técnico sofisticado.
3. Solo si las 3 están bien puestas en Block sin exclusiones jugosas, ahí sí toca buscar evasion de técnica (research reciente, porque lo viejo probablemente ya lo cazaron).

| #   | Capa                                                              | Cuántas reglas la respetan | Alcance                                                                 | Dónde se configura                                                                  |

Fuente: [File and folder exclusions for ASR rules](https://learn.microsoft.com/en-us/defender-endpoint/attack-surface-reduction-rules-overview#file-and-folder-exclusions-for-asr-rules).

#### Dos trampas prácticas

- Excluir algo = menos protección Y menos visibilidad. No genera evento tampoco: es punto ciego total, no solo permiso.
- La exclusión no aplica en caliente. Si el proceso ya estaba corriendo al añadirla, sigue disparando detecciones hasta reiniciarlo.

#### Conflicto entre Group Policy y MDM (Intune)

- Por defecto gana `Group Policy`.
- `MDMWinsOverGP = 1` invierte esa precedencia (solo ajustes compatibles del `Policy CSP`).
- `controlled configuration` evita el conflicto de raíz en vez de resolverlo después.

1. Event Viewer local del dispositivo
2. Informe de `ASR` en el portal
3. `Advanced Hunting`

#### No todo bloqueo genera alerta

De 19 reglas `ASR`, solo 8 generan alerta `EDR` real (la que ve el SOC en `Incidents and alerts`) al bloquear o avisar:

1. `Block persistence through WMI event subscription`
2. `Block Adobe Reader from creating child processes`
3. `Block executable content from email client and webmail`
4. `Block execution of potentially obfuscated scripts`
5. `Block JavaScript or VBScript from launching downloaded executable content`
6. `Block untrusted and unsigned processes that run from USB`
7. `Block Win32 API calls from Office macros`
8. `Use advanced protection against ransomware`

Las otras 11 reglas: bloquean/auditan igual, pero SOLO dejan evento consultable — ningún analista se entera salvo que esté mirando el log activamente.

#### Condición extra dentro de las 8

Las reglas #2, #3 y #5 (Adobe Reader, correo/webmail, JavaScript/VBScript) solo generan alerta si el dispositivo tiene `cloud protection level` en `High plus` o `Zero tolerance`. En nivel normal, bloquean igual pero SIN alertar al SOC.

#### Lectura red team

- Evadir una de las 11 reglas "silenciosas": aunque te bloqueen, no salta alerta, solo queda rastro en log.
- Evadir una de las 8: sí hay alerta, salvo que sea de las 3 con requisito de `cloud protection` alto y el tenant esté en nivel default.

## Microsoft Defender for Office 365

En `Microsoft Defender for Office 365`, esta capa reúne las policies que deciden qué le pasa al mensaje antes de entregarlo, durante la entrega y después. A cada destinatario le aplica una sola policy por función, la primera que le alcance por precedencia, y las demás ni se evalúan. Aquí vive el veredicto y la acción

```
CORREO ENTRANTE
  │
  ├──▶ Edge protection          (si cae aquí no hay mensaje: nada que investigar)
  │      ├─ reputación de IP y de dominio
  │      ├─ filtrado de directorio
  │      ├─ backscatter
  │      └─ límite de volumen
  │
  ├──▶ Sender intelligence      (valida el remitente)
  │      ├─ autenticación de correo: SPF · DKIM · DMARC · ARC
  │      ├─ spoof intelligence                          ◀── anti-phishing
  │      ├─ bulk filtering           (nivel = BCL)      ◀── anti-spam
  │      └─ mailbox intelligence                        ◀── anti-phishing
  │
  ├──▶ Content filtering        (examina el mensaje en sí)
  │      ├─ mail flow rules
  │      ├─ antivirus                               ◀── anti-malware
  │      ├─ reputación de adjuntos y URL            ◀── anti-malware / anti-phishing
  │      ├─ heurística                              ◀── anti-spam / anti-phishing
  │      └─ detonación de Safe Attachments          ◀── MDO, no EOP
  │
  ▼
ENTREGADO AL BUZÓN
  │
  └──▶ Post-delivery protection (actúa sobre lo ya entregado)
         ├─ Safe Links en el momento del clic     ◀── MDO, no EOP
         ├─ ZAP        malware/spam/phishing: sin licencia especial
         │             Teams: exige P1 o P2
         └─ vistas de campaña

``` 

> `ZAP` ya nombra las tres en la propia línea (`malware/spam/phishing`), y se configura desde anti-malware, anti-spam y anti-phishing respectivamente.

- `MDO` protege destinatarios con buzón más los archivos de SharePoint, OneDrive y Teams, pero esas dos últimas protecciones no funcionan igual: `Safe Attachments for SharePoint, OneDrive and Microsoft Teams` y `Safe Documents` son ajustes globales del tenant que se habilitan una sola vez y protegen el archivo esté donde esté, sin asignarse a ningún destinatario ni depender de una policy.
- `EOP` protege correo de buzones de Exchange Online y también de buzones on-premises con el licenciamiento y enrutamiento correspondientes. `ZAP`, en cambio, no actúa sobre buzones on-premises aunque el correo haya pasado por el servicio.
> La regla que unifica las tres: todo en `EOP` y `MDO` se asigna a destinatarios con buzón, salvo las protecciones de archivos de SharePoint, OneDrive y Teams, que son globales del tenant.
### EOP: políticas base de protección

> `EOP` cubre las cuatro fases enteras y funciona solo, sin licencia extra. MDO no añade fases: añade profundidad dentro de ellas. Donde EOP usa reputación, firmas y heurística, MDO detona en sandbox y detecta impersonation

`Exchange Online Protection (EOP)` aporta la protección base incluida con los buzones cloud. Las policies predeterminadas de anti-malware, anti-spam y anti-phishing no son un preset: se aplican a todos los destinatarios, sin filtros ni excepciones; no pueden deshabilitarse ni borrarse, pero sí modificar sus ajustes. No tienen prioridad configurable y son el último recurso cuando no aplica antes una preset o custom policy.

- [ ] Las policies de EOP

- `Anti-malware` detecta malware y envía los mensajes afectados a cuarentena.
- `Inbound anti-spam` clasifica bulk, spam, high confidence spam, phishing y high confidence phishing; el nivel de bulk se expresa como `Bulk Confidence Level (BCL)`. 
- `Outbound anti-spam` controla el correo saliente y el reenvío automático externo.
- `Anti-phishing` aporta anti-spoofing en EOP; MDO añade protección de suplantación de usuarios y dominios y phishing thresholds.
- `Connection filtering` se configura únicamente en la default connection filter policy mediante listas de IP permitidas o bloqueadas.
- `ZAP` vuelve a evaluar mensajes ya entregados con veredictos de malware, spam o phishing.
- Las `Quarantine policies` determinan qué puede hacer el usuario con el mensaje en cuarentena y si recibe notificaciones; no cambian el veredicto que lo llevó allí.

- [ ] Autenticación de correo

| Autenticación de correo | Qué hace |
| --- | --- |
| `Sender Policy Framework (SPF)` | Declara qué servidores pueden enviar en nombre del dominio |
| `DomainKeys Identified Mail (DKIM)` | Firma el mensaje para probar que no se alteró por el camino |
| `Domain-based Message Authentication, Reporting and Conformance (DMARC)` | Valida que al menos una comprobación, `SPF` o `DKIM`, sea correcta y esté alineada con el dominio de `5322.From`. Si ninguna cumple ambas condiciones, `DMARC` falla y la política publicada indica `none`, `quarantine` o `reject` |
| `Authenticated Received Chain (ARC)` | Conserva el resultado de la validación cuando un servicio intermedio reenvía el correo y rompería la comprobación |

La política predeterminada de `anti-phishing` se aplica a todos los destinatarios tanto en la protección base de correo como en `Microsoft Defender for Office 365`. `Microsoft Defender for Office 365` añade protecciones de suplantación de usuarios y dominios y `phishing email thresholds`; los usuarios y dominios que se quieren proteger deben configurarse. Las políticas personalizadas permiten seleccionar destinatarios concretos.

> Los presets no configuran `Outbound anti-spam` ni `Connection filtering`, que se administran por separado. Fuente: [Built-in security features for all cloud mailboxes](https://learn.microsoft.com/en-us/defender-office-365/eop-about).

### Preset security policies: Built-in, Standard y Strict

Microsoft recomienda usar las preset security policies como base y reservar las policies personalizadas para destinatarios que necesiten ajustes distintos.

Las preset security policies `Standard` y `Strict` se asignan mediante `Users`, `Groups` o `Domains`, y los tres filtros resuelven siempre a destinatarios con buzón o mail user; un usuario de Entra ID sin buzón nunca queda cubierto.

Los tres perfiles no se comportan igual:

| Perfil | Asignación y función |
| --- | --- |
| `Built-in protection` | Aporta `Safe Links` y `Safe Attachments` a destinatarios no cubiertos por Standard, Strict o una policy personalizada de la función. No existen policies predeterminadas de Safe Links ni Safe Attachments. Exige al menos una licencia de MDO en el tenant; admite excepciones por usuarios, grupos o dominios, pero no modificar sus ajustes. Prioridad fija `Lowest` |
| `Standard protection` | Baseline recomendado para la mayoría de usuarios; no protege a nadie hasta que se habilita y se le asignan destinatarios |
| `Strict protection` | Configuración más agresiva para usuarios de alto valor o mayor riesgo; tampoco se aplica hasta que se habilita y asigna |

La precedencia es `Strict` → `Standard` → policies personalizadas por prioridad → policy predeterminada o `Built-in protection`. Las policies internas creadas por los perfiles predefinidos no se modifican directamente: se administran habilitando el perfil y cambiando sus asignaciones o excepciones.

### Safe Attachments y Safe Links

- `Safe Attachments` amplía esa protección mediante detonación de archivos antes de entregarlos. Una policy nueva tarda hasta 30 minutos en aplicarse.
	- `Off`: No escanea los adjuntos
	- `Monitor`: Entrega el mensaje aunque detecte malware, y registra el resultado del escaneo
		- `Redirect messages with detected attachments` reenvía a un buzón de análisis los mensajes con adjunto detectado
	- `Block`: Pone el mensaje en cuarentena. Es el valor predeterminado y el que usan los presets `Standard` y `Strict`
		- `Block unscanned attachments`: pone en cuarentena los mensajes con adjuntos cifrados que Safe Attachments no pudo escanear, con exclusiones por tipo de fichero.
	- `Dynamic Delivery (Preview messages)`: Entrega el cuerpo de inmediato sin los adjuntos y los reengancha si el escaneo los da por seguros
- `Safe Links` comprueba las direcciones URL cuando el usuario hace clic. Una policy nueva tarda hasta 6 horas en aplicarse. La página `URL & click protection settings` reparte los ajustes de `Safe Links` en cuatro bloques:
	- `Email`: activa la comprobación y la reescritura de las URL del correo. Dentro, `Apply Safe Links to email messages sent within the organization` extiende la protección al correo interno; `Apply real-time URL scanning for suspicious links and links that point to files` analiza en tiempo real, y su subajuste `Wait for URL scanning to complete before delivering the message` retiene el mensaje hasta terminar; `Do not rewrite URLs, do checks via SafeLinks API only` mantiene la comprobación sin envolver el vínculo.
	- `Do not rewrite the following URLs in email`: excepciones que no se reescriben ni se escanean durante el flujo de correo, aunque todavía pueden bloquearse en el momento del clic. Para exceptuar una URL de verdad se reporta como `I've confirmed it's clean` y se añade a la Tenant Allow/Block List.
	- `Teams` y `Office 365 apps`: activan la protección en esos clientes sin reescribir la URL. El de Teams puede tardar hasta 24 horas en surtir efecto.
	- `Click protection settings`: `Track user clicks` registra el clic, y desmarcar `Let users click through to the original URL` impide que el usuario continúe al sitio desde la página de aviso.

> Las policies personalizadas de `Safe Attachments` y `Safe Links` se aplican a destinatarios concretos mediante usuarios, grupos o dominios aceptados y tienen prioridad respecto de otras policies personalizadas de la misma función. Microsoft recomienda preferir los perfiles `Standard` o `Strict` cuando no se necesite una excepción específica.

Fuentes: [configurar Safe Attachments](https://learn.microsoft.com/en-us/defender-office-365/safe-attachments-policies-configure) y [configurar Safe Links](https://learn.microsoft.com/en-us/defender-office-365/safe-links-policies-configure).

### Tenant Allow/Block List y Advanced Delivery

La Tenant Allow/Block List aplica a email y collaboration; administra domains y email addresses, spoofed senders, URLs, files, IPv6 addresses y Teams domains/addresses. No es una lista global de excepciones para MDE. Un block siempre tiene precedencia sobre un allow.

- Un archivo legítimo bloqueado se envía desde `Submissions` como `I've confirmed it's clean`; no se crea directamente una entrada `Allow` de archivo en la lista.
- Una URL puede permitirse directamente solo para veredictos hasta phishing normal. Para anular malware o phishing de alta confianza debe enviarse a Microsoft mediante `Submissions`.
- Las entradas `Allow` de dominios, direcciones de correo, archivos y direcciones `URL` tienen caducidad administrada; las de `spoofed senders` no caducan. Microsoft puede retirar entradas temporales cuando ya no son necesarias. Para simulaciones de phishing de terceros se usa `Advanced delivery`, no esta lista.
- Permitir un elemento solo omite los filtros asociados a esa entidad; el resto de las comprobaciones del mensaje sigue aplicándose.
- Un block de sender/domain clasifica el message como high confidence phishing; un file block como malware y un URL block como high confidence phishing. Un IP block rechaza el inbound message en el service edge.

## Microsoft Defender for Identity

## Microsoft Defender for Cloud Apps

```
Microsoft Defender for Cloud Apps (security.microsoft.com > Cloud apps: Cloud discovery)
  │
  ├──▶ log collector — Cloud Discovery (ve y etiqueta Unsanctioned, no bloquea por sí sola)
  │     ├──▶ Microsoft Defender for Endpoint (acota por device groups, puede avisar en vez de cortar)
  │     ├──▶ Zscaler NSS / iboss / Corrata / Menlo / Open Systems (bloquea, sin acotar ni avisar)
  │     └──▶ Block script exportado a appliance on-premises
  │
  ├──▶ API connector (fuera de banda, actúa después del hecho: suspende, revoca token, cuarentena, etiqueta)
  │     └──▶ File policies (Policy management > Information Protection > Create policy > File policy)
  │
  └──▶ reverse proxy — Conditional Access App Control (tiempo real, dentro de la sesión: bloquea/limita download, upload, copy, print)
        ├──▶ Access policy (Audit | Block sobre la entrada)
        └──▶ Session policy (Monitor only | Block activities | Control download | Control upload → Audit | Block | Protect)
```

En `Microsoft Defender for Cloud Apps`, esta capa es un `Cloud Access Security Broker` (CASB): media entre los usuarios y las apps SaaS que consumen, sean de Microsoft o de terceros (`Salesforce`, `Box`, `Dropbox`, `Google Workspace`, `ServiceNow`, `AWS`). Se conecta de tres formas distintas:

1. log collector para `Cloud Discovery`: descubre shadow IT por logs, no bloquea nada por sí solo. Etiquetar `Unsanctioned` (`Cloud discovery > Discovered apps`) solo filtra y vigila. El bloqueo llega por integración, y hay tres caminos:
	- `Microsoft Defender for Endpoint` — permite acotarlo a device groups y avisar al usuario en vez de cortar. Exige habilitar `Enforce app access` en `Cloud discovery > Microsoft Defender for Endpoint` (sincroniza `sanctioned/unsanctioned` como indicadores de red), `Custom network indicators` activo en `Optional features`, y en el dispositivo `Microsoft Defender Antivirus` en modo activo con `real-time protection`, behavior monitoring, cloud-delivered protection y `Network protection` en `Block`.
    - `Zscaler NSS`, `iboss`, `Corrata`, `Menlo` u `Open Systems` — bloquean pero sin acotar ni avisar.
    - Block script exportado para un appliance on-premises.
2. `API connector` para apps ya sancionadas: MDCA habla con la app por su API, fuera de banda — no ve ni corta la sesión en vivo. Actúa después del hecho: suspende usuario, revoca token, pone en cuarentena un archivo, o aplica etiqueta. Escanea archivos cada 12 horas, más revisión casi inmediata si detecta un cambio.
	- `File policies`: Ubicado en `security.microsoft.com > Cloud apps > Policies > Policy management > (pestaña) Information Protection > Create policy > File policy` inspecciona el contenido de los ficheros de las aplicaciones conectadas, en tiempo real y en reposo, y aplica governance actions cuando hay coincidencia: lanzar alerta y notificación por correo, cambiar el acceso compartido del fichero, ponerlo en cuarentena de administrador para que alguien lo revise, aplicar o quitar una sensitivity label de Purview, quitar permisos de fichero o carpeta, y moverlo a la papelera.
3. reverse proxy para `Conditional Access App Control`: es la capa que controla en tiempo real quién entra a la app y qué puede hacer dentro (bloquea o limita `download`, `upload`, `cut/copy/paste`, `print`). Actúa ella misma como reverse proxy de sesión: no depende de `MDE` ni de un proxy externo, el bloqueo lo aplica MDCA en el momento. `security.microsoft.com > Cloud apps > Policies > Policy management > Conditional Access > Create policy` (requiere una Conditional Access policy de Entra: `entra.microsoft.com > Entra ID > Conditional Access > Policies > Access controls > Session > Use Conditional Access App Control`).
	- Una `Access policy` evalúa usuario, ubicación, dispositivo y aplicación, y su acción es `Audit` o `Block` sobre la entrada.
	- Una `Session policy` controla actividades dentro de la sesión; si dos coinciden, se aplica la más restrictiva. Se define con un `Session control type` —`Monitor only`, `Block activities`, `Control file download (with inspection)`, `Control file upload (with inspection)`— más una `Action`: `Audit`, `Block`, o `Protect` (solo en download, aplica `sensitivity label` en vez de bloquear). Ejemplo de `Block activities`: cortar el envío de un mensaje sensible en Teams o Slack.

## Microsoft Defender for Cloud

> `Microsoft Defender for Cloud > Environment settings`

```
Microsoft Defender for Cloud
  │
  ├──▶ CSPM — evalúa configuración (nunca alertas, se corrige)
  │
  ├──▶ CWPP — por workload (único con alertas runtime, se investiga)
```
 
`Defender for Cloud` son "planes" que enciendes por `suscripción/cuenta/proyecto`, y cada uno hace una cosa distinta. Si algo te sale como recomendación, la arreglas tú (es un hueco de configuración). Si te sale como alerta, es que ya pasó algo raro y tienes que investigarlo

1. `Cloud Security Posture Management` (`CSPM`): solo revisa configuración. Te dice "esto está mal puesto" y da recomendaciones y `Cloud Secure Score`. `Foundational CSPM` es gratis, `Defender CSPM` de pago.
    - Cadena de postura, jerarquía de arriba a abajo:
        - `security policy`: a qué scope (suscripción, management group) le aplicas qué standards.
        - `security standard`: el checklist contra el que te comparan (ej: MCSB).
        - `recomendación`: lo que sale cuando un recurso no pasa una regla de ese checklist.
    - Los 3 tipos de standard:
        - Benchmarks integrados: checklist ya hecho por Microsoft (`Microsoft Cloud Security Benchmark` / `MCSB`, por defecto; antes `Azure Security Benchmark`). AWS le suma `AWS Foundational Security Best Practices`, GCP le suma `GCP Default`. Se siguen en `Regulatory compliance`.
        - Cumplimiento normativo: checklist para pasar una auditoría (ISO, PCI...), sobre iniciativas de `Azure Policy`.
        - Personalizado: el checklist lo escribes tú en `KQL`, necesita `Defender CSPM` (pago).
    - Dos scores:
        - `Secure Score` clásico (portal Azure): cuenta simple, % de recursos sanos por control, solo mira el MCSB. Fórmula: `current score = max score × healthy resources / (healthy resources + unhealthy resources)`.
        - `Cloud Secure Score` (portal Defender): no cuenta, pesa — una recomendación grave en un recurso expuesto pesa más que una menor en uno aislado (nivel de riesgo + risk factors + criticidad).
        - Los dos suben igual: corriges a mano o le das a `Fix`, en `Unhealthy resources`.
2. `Cloud Workload Protection Platform` (`CWPP`) no es simplemente lo opuesto: se habilita por workload y es el único que genera alertas de runtime, pero además aporta sus propias recomendaciones, guía de hardening y evaluación de vulnerabilidades sobre ese workload.
    - En `Defender for Containers`, tras habilitar el plan para la suscripción o el conector multicloud se configuran sus componentes: agentless scanning, `Defender sensor`, `Azure Policy for Kubernetes`, acceso a la API de Kubernetes y acceso a los registros para escanear imágenes. Los clústeres externos se incorporan mediante Azure Arc o los conectores de AWS y GCP.

## Microsoft Purview

En `Microsoft Purview`, esta capa reúne las policies que vigilan el dato y la conducta del usuario que lo maneja. En ninguna de las dos, un `policy match` equivale a alerta: solo alerta si la rule está configurada para ello.

```
Microsoft Purview
  │
  ├──▶ Insider Risk Management — vigila personas, no contenido. Puntúa qué tan probable es que alguien haga algo malo con datos.
  ├──▶ Data Loss Prevention — vigila contenido, no personas. Mira qué hace la gente con archivos/datos sensibles.
```

1. `Insider Risk Management` (`IRM`): vigila personas, no contenido. Puntúa qué tan probable es que alguien haga algo malo con datos.
    - Una policy dice: a quién vigilo, qué evento lo mete en la vigilancia (`triggering event`, ej: se marca como usuario saliente), qué señales suman puntos, cuánto puntaje hace falta, y en qué ventana de tiempo.
    - Las plantillas te dan una config ya armada para arrancar — ej: `Data theft by departing users`, pilla a alguien llevándose datos justo antes de irse, se puede disparar solo con borrarle la cuenta de Entra.
    - Sin ese evento disparador, nadie entra solo (aunque puedes meter gente a mano). Sin señales que apliquen, no hay nada que puntuar — no pasa nada.
2. `Data Loss Prevention` (`DLP`): vigila contenido, no personas. Mira qué hace la gente con archivos/datos sensibles.
    - Una policy junta: dónde vigilar (`locations`), a quién (`users`/`groups`), bajo qué condición (`conditions`), y qué hacer si pasa (`actions`).
    - Si algo coincide puede: solo anotarlo (`audit`), avisarle al usuario, restringirle el acceso, o bloquear de plano (`Block`, o `Block with override` si le dejas saltárselo). Ojo: que coincida no significa que te avise — solo alerta si tú configuraste esa rule para alertar.
    - Antes de activarla en serio, la corres en `Simulation mode` para ver a quién le hubiera pegado, sin bloquear a nadie todavía.
## Microsoft Entra ID Protection

```
Microsoft Entra ID Protection
  │
  ├──▶ User risk policy — probabilidad de cuenta comprometida
  ├──▶ Sign-in risk policy — la sesión concreta
  ├──▶ MFA registration policy — obliga a registrar métodos MFA
```

En `Microsoft Entra ID Protection`, esta capa reúne únicamente las políticas que responden al riesgo. El umbral de cada política es la decisión de diseño: alto la dispara pocas veces y molesta poco, pero deja fuera detecciones `Low`/`Medium` —donde un atacante puede moverse—; bajo protege más e interrumpe más. Las políticas basadas en `User risk` y `Sign-in risk` se configuran por separado en `Microsoft Entra ID > Conditional Access > Policies`. Las políticas `legacy` de ID Protection se retiran el 1 de octubre de 2026 y se migran a `Conditional Access`.

1. `User risk policy`: mide qué tan robada está la CUENTA en general (no esta sesión, la cuenta). Microsoft dice: pon el umbral en `High` y usa `Require risk remediation` — si el usuario tiene contraseña, lo obligas a cambiarla después de pasar MFA; si es `passwordless`, lo obligas a autenticarse de nuevo después de matarle las sesiones activas. Ojo: ese cambio de contraseña NO es el "olvidé mi contraseña" de siempre (`SSPR`), es otro mecanismo aparte
2. `Sign-in risk policy`: mide qué tan rara es ESTA sesión de ahora, no la cuenta en general. Recomendado: dispararla desde `Medium` para arriba, pidiendo MFA cuando salta.
3. `Multifactor authentication registration policy`: obliga a la gente a registrar su MFA (tener el Authenticator configurado, etc.) antes de que lo necesiten de verdad.

Las 3 dejan excluir usuarios — ahí van las cuentas `break-glass` (revisar de vez en cuando, no dejarlas olvidadas). Marcar una red como de confianza baja los falsos positivos. Con workload identities, Conditional Access solo bloquea service principals de TU propio tenant — SaaS de terceros, apps multitenant y managed identities quedan fuera, no los toca.

# 4 · Ingesta

La `ingesta` es el recorrido completo del dato desde su recopilación o recepción en el origen hasta su almacenamiento en la tabla. Ese recorrido tarda: cada fila guarda cuándo ocurrió el evento en el origen, en `TimeGenerated` en las tablas del workspace de Sentinel y en `Timestamp` en las tablas nativas de Defender XDR, y en ambos casos `ingestion_time()` devuelve cuándo quedó escrita en la tabla. La diferencia entre las dos es la latencia de ingesta, que depende de cada fuente y que las reglas de detección tienen que tener en cuenta (ver `# 7 · Detección y alertas > ## Las reglas que escribe el analista > ### Reglas Scheduled`). La tabla siguiente relaciona el origen, el conector, el tipo de conexión, la configuración y la transformación —cuando corresponda— que hacen posible ese recorrido.

Este capítulo cubre únicamente la ruta hacia el workspace de Sentinel. La ruta nativa no aparece en el mapa siguiente porque no tiene conector ni mecanismo de ingesta que configurar: la telemetría de `MDE`, `MDO`, `MDI` y `MDCA` se escribe sola en el `XDR default tier` en cuanto el workload está licenciado e incorporado, y desde ahí se consulta en `Advanced Hunting` sin ningún paso intermedio. ## Origen

Un origen es el workload, sistema, servicio, dispositivo, recurso, aplicación o proveedor que genera los datos o señales iniciales que se quieren ingerir. No es el conector que habilita su flujo, el mecanismo que los recopila ni la tabla que los almacena.

## Conector o ruta

Los conectores integrados o instalados mediante soluciones de `Content hub` vinculan el origen con Microsoft Sentinel. Para el examen, hay que elegirlos según el tipo de dato, los requisitos del origen y la tabla que necesita la detección.

- [ ] Microsoft Defender XDR

- `Connect incidents & alerts`: sincroniza incidentes y alertas.
- `Connect entities`: incorpora identidades de Active Directory local mediante `MDI`; exige `UEBA`.
- `Connect events`: ingiere las tablas de `Advanced Hunting` seleccionadas.

- [ ] Microsoft Entra ID, Microsoft 365 y Purview

- `Microsoft Entra ID`: exporta las categorías de activity logs seleccionadas.
- `Microsoft Entra ID Protection`: integra alertas mediante su conector independiente o mediante `XDR`.
- `Microsoft 365`: integra la auditoría de los `workloads` habilitados.
- `Microsoft Purview Information Protection`: integra eventos de protección de información.
- `Microsoft 365 Insider Risk Management`: integra sus alertas exportadas.
- `Microsoft Purview Data Loss Prevention`: integra alertas, incidentes y actividad relacionada mediante `XDR`.

- [ ] Microsoft Defender for Cloud

- Conector `tenant-based` o `subscription-based`: integra las alertas directamente.
- Integración `XDR`: incorpora sus alertas a los incidentes de `XDR`.
- `Diagnostic settings`: exporta aparte los resource logs de los recursos protegidos.

- [ ] Otros conectores

Las soluciones de `Content hub` proporcionan conectores para otras nubes, dispositivos y aplicaciones. Si no existe uno adecuado, se utiliza `CCF`, `Logs Ingestion API` o código propio. Los indicadores de amenazas se integran mediante `TAXII` o `Threat Intelligence Upload API` y se desarrollan en `Threat Intelligence`.

## Tipo de conexión

El tipo de conexión clasifica la ruta técnica entre el origen y Sentinel: mediante API, Diagnostic settings, un agente o una integración directa service-to-service. No recopila datos; solo indica qué clase de ruta se utiliza.

- `API-based`: conexión que obtiene o recibe registros mediante una `API`.
- `diagnostic settings-based`: exportación de categorías de registros mediante `Diagnostic settings`.
- `agent-based`: recopilación mediante un agente instalado; `Windows agent-based` es la variante para Windows. Las rutas `Syslog`, `CEF` y archivos mediante `AMA` también usan agente.
- `service-to-service`: integración directa entre servicios, administrada por Microsoft.

`Tenant-based` y `subscription-based` indican el alcance de los conectores independientes de `Defender for Cloud`; `Custom code` indica una implementación personalizada. `Connect entities` hereda `service-to-service` del conector `XDR`, porque esa opción no tiene una clasificación separada.

## Data collection method

El `Data collection method` es el mecanismo o componente que recopila y entrega los datos; el valor de cada fila está en `## Mapa principal`. Solo las cadenas de varios pasos se expanden acá:

- `Azure Monitor Agent (AMA)`: agente que recopila y envía datos según una `DCR`.
- `Windows Event Forwarding (WEF)` → `Windows Event Collector (WEC)` → `AMA`: reenvía eventos de Windows hasta `AMA`.
- `Syslog` → `AMA`: el demonio `Syslog` entrega los mensajes a `AMA`.
- `Common Event Format (CEF)` sobre `Syslog` → `AMA`: el formato `CEF` viaja por `Syslog` hasta `AMA`.

## Configuración clave

Son los parámetros, permisos y recursos necesarios para que funcione cada ruta de la tabla. Los siguientes apartados desarrollan las configuraciones evaluadas por la guía del examen.

### Microsoft Defender XDR

`Connect incidents & alerts` solo sincroniza con el workspace primario. Al habilitarlo, los conectores de alertas independientes de los componentes integrados se desconectan en segundo plano, aunque puedan seguir apareciendo conectados. Esos conectores heredados solo traían la alerta, nunca el dato crudo: el dato en bruto para hunting llega por `Connect events` del conector `XDR`. Si Sentinel está incorporado al portal de Defender, el conector `XDR` se habilita automáticamente para ese workspace; en caso contrario, se configura desde su página.

La sustitución de conectores independientes puede cambiar el esquema de las alertas. `Connect events` recopila únicamente las tablas compatibles seleccionadas, como `AlertInfo`, `AlertEvidence`, `DeviceEvents`, `EmailEvents`, `IdentityDirectoryEvents`, `IdentityLogonEvents`, `IdentityQueryEvents` y `CloudAppEvents`. No ingiere `DeviceTvm*`: estas se consultan en Advanced Hunting y requieren una ruta personalizada hacia el workspace.

### Microsoft Entra ID, Microsoft 365 y Purview

- `Microsoft Entra ID`: autorizar el tenant y elegir las categorías y el workspace de destino.
- `Microsoft Entra ID Protection`: elegir entre el conector independiente y la integración `XDR`.
- `Microsoft 365`: conectar el tenant y habilitar los workloads compatibles.
- `Purview Information Protection`: habilitar la auditoría y las etiquetas, y autorizar el tenant.
- `Insider Risk Management`: disponer de licencia, políticas que produzcan alertas y exportación habilitada.
- `Purview DLP`: habilitar el conector `XDR` y `CloudAppEvents` para la actividad relacionada.

### Microsoft Defender for Cloud

En el portal de Azure se configura `Tenant-based Microsoft Defender for Cloud (Preview)` o `Subscription-based Microsoft Defender for Cloud (Legacy)`; con el segundo se conectan todas las suscripciones relevantes. Con Sentinel incorporado al portal de Defender y la integración `XDR`, las alertas se reciben mediante `XDR`. La solución de `Defender for Cloud` aporta el contenido integrado de Sentinel.

`Alert synchronization` y `bi-directional sync` no son lo mismo. Al conectar `Defender for Cloud`, el estado de la alerta se sincroniza entre ese producto y Sentinel, pero cambiar el estado de la alerta no cambia el del incidente de Sentinel que la contiene. Con `bi-directional sync`, el estado del incidente de Sentinel también se propaga hacia la alerta original: cerrar el incidente cierra esa alerta en `Defender for Cloud`. No es la sincronización de dos incidentes paralelos.

### Configuración de API y conectores personalizados

- `CCF`: definir autenticación, endpoint, paginación cuando corresponda y destino.
- `Logs Ingestion API`: crear la tabla, configurar el stream de entrada y el destino en una `DCR`, y conceder a la identidad que envía el rol `Monitoring Metrics Publisher` sobre la `DCR`.
- `Logic App`, `Azure Function` o aplicación cliente: configurar el código, la autenticación, la ejecución y la interfaz de entrega.

Se usa el endpoint de ingesta de la `DCR` cuando está disponible. Se necesita un `DCE` con `Private Link` o cuando la `DCR` no tiene endpoint propio.

### Windows Security Events y WEF

`AMA` recopila los datos; la `DCR` define qué se recoge, su transformación y el destino; la `Data Collection Rule Association (DCRA)` asocia la regla con la máquina o recurso.

El conector recoge de máquinas virtuales de Azure con versiones compatibles de Windows, tanto Server como cliente, y sin importar la región donde estén desplegadas. Las máquinas fuera de Azure necesitan antes el `Azure Connected Machine agent` para incorporarse como recurso de `Azure Arc`: hasta que no aparecen como recurso, no son seleccionables en la `DCR`. Son dos agentes distintos — `Arc` las vuelve un recurso de Azure, `AMA` recopila.

La `DCR` se crea en la misma región que el `Log Analytics workspace` de destino, aunque las máquinas que se le asocian pueden estar en cualquier suscripción o resource group del tenant. Para enviar datos entre tenants distintos hace falta habilitar antes `Azure Lighthouse`.

- [ ] Conjuntos de eventos

- `All Events`: todos los eventos de los canales `Security` y `AppLocker`.
- `Common`: conjunto orientado a auditoría, con la traza completa de usuario — incluye inicio y cierre de sesión (`4624` y `4634`), cambios en grupos de seguridad y operaciones Kerberos de controlador de dominio. Su objetivo es bajar el volumen manteniendo la traza, no filtrar eventos concretos.
- `Minimal`: conjunto corto de eventos que pueden indicar una brecha, sin traza de auditoría completa — incluye inicios de sesión correctos y fallidos (`4624` y `4625`) y creación de procesos (`4688`), pero deja fuera el cierre de sesión `4634`, que es alto en volumen y poco útil para detección.
- `Custom`: eventos definidos mediante consultas `XPath` en la `DCR`.

`Windows Security Events via AMA` escribe en `SecurityEvent`. La recopilación genérica de Windows Event Logs mediante `AMA` escribe en `Event`. `AMA` solo admite `XPath` versión 1.0.

`Sysmon` no es un conector ni determina la tabla: es un servicio de Windows que escribe su telemetría de procesos, conexiones y ficheros en el canal `Microsoft-Windows-Sysmon/Operational`, que se selecciona por `XPath` con `Microsoft-Windows-Sysmon/Operational!*`. La tabla depende de la ruta: una `DCR` genérica de Windows Event Logs lo deja en `Event`, y reenviado por `WEF` hacia un colector acaba en `WindowsEvent`.

- [ ] Windows Event Forwarding

`WEF` reenvía los eventos elegidos desde los equipos origen hacia un `Windows Event Collector (WEC)`; `AMA` los recoge en el colector y `Windows Forwarded Events` los escribe en `WindowsEvent`.

- En una suscripción iniciada por el origen, los clientes descubren el colector mediante la configuración distribuida, normalmente por `GPO`.
- En una suscripción iniciada por el colector, el `WEC` define explícitamente los equipos origen.

`WEF` no habilita la auditoría ni los canales: el evento debe generarse antes de poder reenviarse. Muchas reglas integradas consultan `SecurityEvent`; si el dato llega a `WindowsEvent`, debe elegirse la ruta adecuada o adaptarse la consulta.

### Syslog y CEF mediante AMA

`Syslog` es el transporte y `CEF` es un formato que viaja sobre `Syslog`. En un `forwarder` Linux la fuente entrega los mensajes por `TCP` o `UDP` al puerto `514` —o al que se configure— del demonio `rsyslog` o `syslog-ng`, y es el demonio quien se los pasa a `AMA`, no `AMA` quien escucha ese puerto; `AMA` los procesa según la `DCR` y los envía al workspace. El asistente del conector instala `Azure Monitor Agent (AMA)` en las máquinas seleccionadas al crear la `Data Collection Rule (DCR)`, pero si el forwarder recibe mensajes de otras máquinas todavía hay que ejecutar el installation script para configurar el demonio, la escucha y los puertos locales.

- `Syslog via AMA`: para cada `facility` la `DCR` fija un nivel mínimo y recoge ese nivel y todos los de mayor severidad, y `NONE` desactiva esa `facility`; escribe en `Syslog`. Solo llegan parseadas las cabeceras: el mensaje en bruto queda en la columna `SyslogMessage`, así que para consultar sus campos hay que escribir un parser.
- `Common Event Format (CEF) via AMA`: recibe `CEF` mediante el `forwarder`; escribe en `CommonSecurityLog` con los campos ya separados en columnas predefinidas.

Cuál de las dos se usa no es cuestión de preferencia: depende de si la fuente emite `CEF` o `Syslog` ordinario, y la solución instalada desde Content hub indica cuál corresponde. La máquina Linux que recibe puede ser el propio origen o un forwarder dedicado, en Azure, on-premises o en otra nube; si no es una máquina virtual de Azure hay que incorporarla antes como `Azure Arc-enabled server` con el `Azure Connected Machine agent` para poder asociarla a la `DCR` e instalar `AMA`.

Si una misma `facility` se recoge por las rutas `Syslog` y `CEF`, el evento puede duplicarse en `Syslog` y en `CommonSecurityLog`. Se evita separando las facilities de cada stream; si el appliance no permite cambiarlas, una transformación de ingesta en la `DCR` filtra los mensajes `CEF` del stream `Syslog`.

### Actividad de Azure mediante Diagnostic settings

Un `diagnostic setting` selecciona las categorías que se exportan y su destino. Para que los registros sean consultables mediante KQL en Sentinel, el destino debe ser un `Log Analytics workspace`.

- El `Activity Log` de la suscripción llega a `AzureActivity`.
- Los `resource logs` se habilitan en el recurso o subrecurso y llegan a la tabla correspondiente.
- Las categorías de `Entra ID` se habilitan en el ámbito del `tenant`; el permiso sobre este y el acceso al destino se revisan por separado.

Para desplegar `Diagnostic settings` a escala se usa `Azure Policy` con efecto `DeployIfNotExists`. La asignación necesita una identidad administrada con permisos para crear los settings. Los recursos existentes requieren una `remediation task`; los nuevos se configuran cuando la política los evalúa.

El asistente `Launch Azure Policy Assignment Wizard` del conector `Azure Activity` despliega los `Diagnostic settings` mediante `Azure Policy`; también se pueden configurar directamente los `Diagnostic settings`. Ambas rutas envían el `Activity Log` a `AzureActivity`.

### Custom Data Collection de MDE

`Custom Data Collection (Preview)` recoge eventos adicionales de dispositivos incorporados a `Microsoft Defender for Endpoint` y los envía a `Microsoft Sentinel`, sin sustituir la telemetría `Device*` habitual. Requiere `Microsoft Defender for Endpoint Plan 2`, un `workspace` de `Microsoft Sentinel` seleccionado y, para alcance selectivo, etiquetas dinámicas de `Asset Rule Management`.

`security.microsoft.com` > `Settings` > `Endpoints` > `Rules` > `Custom Data Collection` → seleccionar `workspace`, tabla de eventos de origen y acción → definir filtros → establecer alcance → crear la regla.

La regla escribe en `DeviceCustomProcessEvents`, `DeviceCustomImageLoadEvents`, `DeviceCustomFileEvents`, `DeviceCustomNetworkEvents` o `DeviceCustomScriptEvents`, según el tipo de evento.

## Transformación

Una transformación de ingesta procesa los registros antes de almacenarlos: puede filtrar filas, quitar columnas o adaptar el esquema. Su disponibilidad y configuración dependen de la ruta y de las tablas compatibles.

Su consulta se escribe contra `source`, que no es una tabla almacenada sino la tabla virtual que representa el stream de entrada: se aplica a cada registro entrante y debe devolver columnas que encajen con la tabla de destino, filtrando con `where`, calculando con `extend` y dando forma con `project`.

- `AMA` y `Logs Ingestion API`: la transformación se define en la `DCR` que controla ese flujo.
- Conectores `CCF` compatibles: se utiliza la `DCR` creada para el conector.
- Rutas sin `DCR` propia: pueden utilizar una `Workspace transformation DCR` cuando el conector y la tabla lo admiten. Hay una por `workspace`, que puede contener transformaciones para varias tablas.

En `Logs Ingestion API`, el esquema del stream de entrada puede diferir del esquema final cuando la transformación realiza el mapeo.

El soporte debe comprobarse en la referencia del conector; no se deduce únicamente de que sea `API-based` ni del nombre de la tabla. [Flujo y soporte de transformaciones](https://learn.microsoft.com/en-us/azure/sentinel/data-transformation#data-ingestion-flow-in-microsoft-sentinel).

## Tabla

La columna `Tabla` identifica dónde termina cada flujo. La creación y el esquema se tratan aquí; el plan y la retención están en `Almacenamiento y Retención`, y el significado de los campos en `# 13 · Mapa de tablas y relaciones KQL`.

- [ ] Tablas personalizadas

Para almacenar un formato propio:

1. Crear la tabla en el `Log Analytics workspace`; su nombre termina en `_CL`.
2. Definir el esquema y asegurar la columna `TimeGenerated`.
3. Crear o seleccionar una `DCR` que describa el flujo de entrada, la transformación necesaria y el destino.
4. Hacer coincidir el `outputStream` con la tabla.
5. Asociar la `DCR` con el recurso o autorizar la aplicación que envía los datos.
6. Validar que la tabla recibe filas con el esquema esperado.

Una transformación de la `DCR` puede filtrar o adaptar cada registro antes de almacenarlo; su salida debe coincidir con el esquema de la tabla.

Modificar el esquema de la tabla no actualiza automáticamente las `DCR` que escriben en ella: ambas partes deben revisarse juntas.

- [ ] Reglas de las custom audit retention policies

- Hasta `50` custom policies por organización.
- Toda custom policy gana a la default.
- Entre custom policies, gana el número de prioridad menor: `1` es la máxima, `10000` la mínima.
- La duración se fija al entrar en el auditing pipeline: cambiar después la licencia o la policy solo afecta a records nuevos, nunca a los ya comprometidos.
- Ninguna policy es retroactiva: no recupera ni retiene lo generado antes de crearla.

## 6 · Modelo de costes de Sentinel

Sentinel factura tres grupos distintos:

1. Ingesta: se cobra desde el día 1, por volumen que entra — el precio ya incluye `31 días` de retención. Tarifa según table plan: `Analytics` (PAYG o commitment desde `100 GB/día`) es la más cara pero incluye consulta ilimitada; `Basic`/`Auxiliary`/`Data Lake` bajan el precio de ingesta a cambio de cobrar por consulta o limitar funciones.
	- Prueba gratuita: `10 GB/día` de Analytics, primeros `31 días`, máx. 20 workspaces/tenant. No cubre Logic Apps, BYOML ni Data Lake.
	- Commitment tier: subir cuando quieras; bajar o volver a PAYG exige esperar `31 días` (cualquier cambio reinicia el contador).
	- Data types gratis (sin cargo de ingesta): `AzureActivity`, `SentinelHealth`, auditoría compatible en `OfficeActivity`, ciertas alertas/incidentes en `SecurityAlert`/`SecurityIncident`. Ojo: esto no hace gratis las tablas de eventos crudos que generaron esa alerta (ej. `DeviceEvents`, `EmailEvents`) — esas se pagan aparte, normal. `SentinelAudit` tampoco es gratis.
	- UEBA: sin SKU adicional, pero factura como tabla normal. Suma `SentinelBehaviorInfo`/`SentinelBehaviorEntities` (aditivo, no sustituye logs).
	- Defender for Servers P2: `500 MB/día` por nodo, agrupado entre máquinas de la suscripción. Beneficia las tablas de seguridad elegibles, como `SecurityEvent`, `SecurityBaseline`, `WindowsFirewall` y `MDCFileIntegrityMonitoringEvents`. Para los canales de eventos de Windows, solo cubre `Microsoft-SecurityEvent` → `SecurityEvent`, no Application ni System
2. Almacenamiento: primeros `90 días` de tablas de solución incluidos, gratis. Dos cosas se cobran aparte: 
	- Subir la Analytics retention más allá de eso
	- Los días extra en Data Lake, cuando total retention > Analytics retention.
3. Procesamiento y ejecución: correr un `JOB` (no una consulta normal) se cobra por GB analizado, se dividen en 2:
	- `KQL job`: solo sobre `Data Lake`.
	- `Search job`: con o sin `Data Lake` — sin onboarding también consulta `Analytics` y su long-term retention, además de `Basic`/`Auxiliary`; con onboarding, también puede buscar en `Data Lake`.
	- Una consulta normal (`Logs`/`Advanced Hunting`) dentro de la ventana interactiva de `Analytics` sigue gratis, no es un job.
	- Summary rules sobre `Basic`/`Auxiliary`: se cobra por dato escaneado.
	- `Hunting graph` (¿Cómo están conectadas las cosas / que ruta investigar?) /`Blast radius` (desde esta cuenta comprometida, ¿Que tanto daño podría propagarse?) = portal Defender sin cargo.
	- `Custom graphs` y consultas vía `MCP`: `graph meter`, por hora de cómputo.

## 7 · Optimización y coste del workspace

Orden seguro:

1. Paso 1, el más barato: no dejar que el ruido llegue. Dos formas — cortarlo en el origen (no enviarlo) o filtrarlo al entrar, con una `ingestion-time transformation` en la DCR. Advertencia: lo que descartas aquí no se puede recuperar después, así que es el paso a hacer primero y con más cuidado.
2. Usar split transformation — confirmar qué filas quedan en Analytics y cuáles van a la tabla `_SPLT` de Data Lake.
3. Cambiar table plan o tier — verificar qué alertas, reglas y consultas dejarán de funcionar.
4. Ajustar Analytics y total retention — confirmar requisitos de cumplimiento e investigación.
5. Crear summary rules — conservar el raw data cuando siga siendo necesario para forense.
6. Elegir Pay-as-you-go, commitment tier o pre-purchase plan — dimensionar con volumen estable y respetar el compromiso de 31 días.
7. Separar datos operativos no relacionados con seguridad — evitar cargos de Sentinel innecesarios en el workspace.

`Daily cap`: protección contra picos, no un método normal de ahorro.

- Al alcanzarla: se detiene la recopilación facturable de `Analytics` y `Basic` hasta el reset — pueden perderse eventos.
- `Auxiliary` no está sujeto a esta cap.
- El volumen se mide después de las transformaciones.
- El exceso que entra antes de que se aplique el corte también se factura (el corte no es retroactivo).

`SOC optimization` analiza el workspace y propone cambios, pero no los ejecuta. Sus familias son `Data value`, `Threat-based coverage`, `Risk-based coverage (preview)`, `Similar organizations` y `AI MITRE tagging (preview)`. Las recomendaciones deben contrastarse con necesidades de cumplimiento, investigación y detección
# 6 · Threat Intelligence

La Cyber Threat Intelligence (`CTI`) aporta contexto sobre amenazas. Su forma táctica son los Indicator of Compromise (`IoC`): una dirección IP, un dominio, una URL o un hash asociados a actividad maliciosa, que se cruzan con la telemetría para encontrar coincidencias. Un indicador no es una detección. La inteligencia más amplia describe actores, Tactics, Techniques and Procedures (`TTP`), infraestructura y víctimas.

- Structured Threat Information eXpression (`STIX`) es el formato que describe los objetos y sus relaciones.
- Trusted Automated eXchange of Indicator Information (`TAXII`) es el protocolo utilizado para transportar colecciones de objetos `STIX`.

Un indicador puede incluir vigencia (`ValidFrom` y `ValidUntil`), confianza (`Confidence`), tipo de amenaza, origen y etiquetas. Al alcanzar `ValidUntil`, deja de considerarse válido, aunque sus registros permanecen en las tablas según la retención.

### Reglas `Scheduled`

- `Rule query`: consulta KQL que devuelve las coincidencias, probada antes en `Logs`; debe devolver `TimeGenerated`, porque es la referencia del lookback.
- `Alert threshold` viene por defecto en `Is greater than 0`: la regla alerta si la consulta devuelve al menos una fila. Si por alguna razón (un mantenimiento, por ejemplo) no quieres que alerte durante un tiempo, no se toca el umbral, ni con `0` ni con `-1`: se pausa la regla con `Disable` y se reactiva con `Enable`, sin perder la configuración.
- `Start running` (preview): deja la regla `Enabled` pero retrasa su primera ejecución a una fecha y hora; después sigue la frecuencia normal.

- [ ] Ejemplo con `SigninLogs`

Un usuario inicia sesión a las `10:00` y falla (`Evento A`), y esa fila no llega a `SigninLogs` en el workspace hasta las `10:15`, porque esta tabla tarda unos 15 minutos en escribir cada fila después de que el inicio de sesión ocurre. Ese retraso es una constante de la fuente, la mides tú, y todo lo que sigue (la consulta, los filtros, la tabla de ejecuciones) se construye a partir de él. Todo gira en torno a `TimeGenerated`: el campo de cada fila que guarda cuándo ocurrió el evento de verdad, así que para `Evento A` `TimeGenerated` = `10:00`, mientras que el momento de llegada queda guardado aparte, en `ingestion_time()` = `10:15`. Una regla `Scheduled` decide qué mirar según `TimeGenerated`, porque es la referencia de su lookback, así que tiene que ver ese `10:00` sí o sí. El problema: si la regla corre cada 5 minutos y solo mira los últimos 5 de `TimeGenerated`, a las `10:05` busca de `10:00` a `10:05` y no encuentra nada, porque la fila aún no ha llegado; a las `10:20` la fila ya está, pero busca de `10:15` a `10:20`, y el `10:00` queda fuera. `Evento A` se pierde.

- [ ] Solución

```kql
let ingestion_delay = 15min;
let rule_look_back = 5min;
SigninLogs
| where TimeGenerated >= ago(ingestion_delay + rule_look_back)
| where ingestion_time() > ago(rule_look_back)
| where ResultType != "0"
| summarize FailedAttempts = count(), TimeGenerated = max(TimeGenerated) by UserPrincipalName, IPAddress
| where FailedAttempts >= 10
```

- `ingestion_delay = 15min`: la constante de la fuente. Si la mides mal y pones menos de lo que tarda de verdad, el evento se vuelve a perder.
- `rule_look_back = 5min`: igual a la frecuencia de la regla (`Run query every` = 5 minutos). Es el tramo que separa una ejecución de la siguiente, y los dos `where` lo usan.
- Primer `where`: amplía la búsqueda en `TimeGenerated` a 20 minutos (15 de retraso más 5 de frecuencia). Así un `TimeGenerated` de `10:00` sigue dentro cuando la fila por fin llega.
- Segundo `where`: como el primero vuelve a mirar los mismos 20 minutos en cada ejecución, este se queda solo con lo que llegó en los últimos 5 minutos según `ingestion_time()`, para no alertar dos veces.
- Las tres últimas líneas son la detección en sí: fallos (`ResultType != "0"`) agrupados por usuario e IP, con un umbral de 10.

| Ejecución | `TimeGenerated >= ago(20min)`            | `ingestion_time() > ago(5min)`                                | Resultado       |
| --------- | ---------------------------------------- | ------------------------------------------------------------- | --------------- |
| `10:05`   | `09:45–10:05` → evento `10:00` **entra** | `>10:00–10:05` → aún no fue ingerido                          | Nada            |
| `10:10`   | `09:50–10:10` → evento `10:00` **entra** | `>10:05–10:10` → aún no fue ingerido                          | Nada            |
| `10:15`   | `09:55–10:15` → evento `10:00` **entra** | `>10:10–10:15` → ingerido a `10:15`, **entra**                | ✅ Se cuenta     |
| `10:20`   | `10:00–10:20` → evento `10:00` **entra** | `>10:15–10:20` → ingerido exactamente a `10:15`, **NO entra** | ✅ Sin duplicado |

1> El primer filtro usa `>=`, así que su inicio está incluido. El segundo usa `>`, así que su inicio está excluido. Por eso `10:15:00` cae solo en la ejecución de las `10:15`.

### Reglas `NRT`

Una regla `NRT` es la misma idea sin margen temporal que configurar: corre cada minuto sobre lo que se ingirió en el minuto anterior. Ordena por tiempo de ingesta y no por el del evento, pero esa ventana la aplica la plataforma, así que no se escribe en la consulta. Se usa cuando la demora importa más que el tamaño de la ventana.

- El límite del servicio es de 50 reglas `NRT` habilitadas y 100 en total.
- Funcionan con fuentes cuya latencia de ingesta sea inferior a 12 horas, aunque pierden sentido práctico mucho antes de ese techo.
- Pueden consultar varias tablas y varios workspaces; el tope multi-workspace de cualquier regla analítica es de 20 workspaces por consulta.
- Si se alerta por evento, una ejecución produce como máximo 30 alertas: 29 individuales y una trigésima que resume el resto.
- Admiten `Entity mapping`, `Custom details`, detalles dinámicos, supresión y automatización igual que las `Scheduled`.

> El límite de `NRT` no se aplica a `Continuous (NRT)` de las custom detections: son mecanismos distintos.

### Custom detection rules de Defender XDR

> solo leen tablas en Analytics tier; en Basic, Auxiliary o solo en Data Lake, ninguna funciona salvo que promuevas el dato a Analytics, o lo materialices ahí con una summary rule o un KQL job

- Asistente de `custom detection rules`: sigue listando `Initiate investigation` entre las acciones sobre dispositivos.
- Página de `automated investigations` (MDE): desde el 1/09/2026, `AIR` ya no se ejecuta como experiencia separada ni admite disparo manual; sus capacidades quedan integradas en la protección antivirus predeterminada.
- Para el alcance real de `AIR` manda la segunda; la primera solo describe lo que aparece en el portal

- [ ] Ejemplo con `SigninLogs` en `Custom detection rule` (workspace)

Mismo caso: `Evento A` ocurre a las `10:00` (`TimeGenerated` = `10:00`) y la fila llega a `SigninLogs` a las `10:15` (`ingestion_time()` = `10:15`). `SigninLogs` es una tabla del workspace, así que la regla solo puede leerla con el workspace incorporado al portal de Defender. La diferencia con `Scheduled` es que aquí no escribes ningún truco: la regla evalúa `ingestion_time()` por su cuenta, y el lookback se cuenta según cuándo llegó la fila, no según cuándo ocurrió. Por eso Learn pide no filtrar la consulta por `TimeGenerated` ni por `Timestamp`, y por eso pueden entrar filas con un `TimeGenerated` más viejo que el lookback.

- [ ] Frecuencia periódica: `Every hour`, lookback de 1 hora (workspace)

> El `lookback` de 1 hora se pone manualmente en el asistente de la regla (`Frequency` = `Every hour`, `Lookback` = 1 hora), no en el KQL. La consulta no lleva ningún filtro de tiempo.

```kql
SigninLogs
| where ResultType != "0"
| summarize FailedAttempts = count(), TimeGenerated = max(TimeGenerated) by UserPrincipalName, IPAddress
| where FailedAttempts >= 10
```

| Ejecución | Filas que llegaron (`ingestion_time()`) | Resultado |
| --- | --- | --- |
| `10:00` | De `09:00` a `10:00`: `Evento A` aún no llegó | Nada |
| `11:00` | De `10:00` a `11:00`: llegó a las `10:15`, entra | Alerta, única vez |
| `12:00` | De `11:00` a `12:00`: ya no entra | Sin duplicado |

- Sin `ingestion_delay` ni `rule_look_back`: el retraso lo absorbe la plataforma.
- Si el lookback es mayor que la frecuencia y el mismo evento cae en dos ejecuciones, la regla lo deduplica sola.
- El precio de la frecuencia periódica: `Evento A` pasó a las `10:00` y la alerta sale a las `11:00`.

- [ ] Frecuencia `Continuous (NRT)` (workspace)

```kql
SigninLogs
| where UserPrincipalName == "breakglass@contoso.com"
```

- Cualquier inicio de sesión de la cuenta de emergencia alerta. La regla evalúa cada fila por evento en cuanto llega: `Evento A` llega a las `10:15` y alerta en ese momento, sin esperar a ninguna ejecución.
- La latencia de la fuente sigue ahí: la alerta no puede salir antes de las `10:15`, porque hasta entonces la fila no existe.
- Requisitos: una sola tabla de la lista de compatibles (`SigninLogs` lo es), sin `join`, `union`, `externaldata` ni comentarios, y solo con las características KQL admitidas.
- No confundir con la regla `NRT` de Sentinel: aquí `Continuous (NRT)` es solo una frecuencia de `Custom detection rule`

- [ ] Ejemplo con `DeviceProcessEvents` en `Custom detection rule` (nativo de Defender)

`Evento C`: en un endpoint corre `rundll32.exe comsvcs.dll, MiniDump` contra `lsass.exe`, una técnica típica de volcado de credenciales. `DeviceProcessEvents` es nativa de MDE, está en la lista de compatibles con `Continuous (NRT)`, y a diferencia de `SigninLogs` no necesita workspace incorporado ni tier de Sentinel: se lee directo.

```kql
DeviceProcessEvents
| where FileName =~ "rundll32.exe"
| where ProcessCommandLine has "comsvcs.dll" and ProcessCommandLine has "MiniDump"
```

- Frente a las frecuencias fijas (1, 3, 12, 24 h), donde el lookback grande absorbe la latencia de MDE sin que te enteres, en Continuous (NRT) no hay ese colchón.
- La latencia de la telemetría de MDE suele ser de segundos, no de los 15 minutos de SigninLogs: por eso Continuous (NRT) rinde mejor sobre tablas nativas de Defender que sobre datos de Sentinel.
- `DeviceId` identifica el dispositivo del evento, y Defender lo necesita para aplicar el `device-group scope` de la regla y saber sobre qué dispositivo actuar; `ReportId` identifica el evento dentro del reporte del sensor de MDE, y Defender lo usa para reconstruir el `process tree` de la investigación; en esta consulta las dos ya vienen incluidas solas, porque no hay `project` ni `summarize` que recorte las columnas.

- [ ] Columnas recomendadas en la consulta de `Custom detection rule`

> Learn las llama recomendadas, no obligatorias: sin ellas la regla se crea igual, pero pierde hora exacta, evento original, scope o entity mapping.

- En tablas de MDE, `DeviceId` y `ReportId`: conservan el device-group scope y permiten construir el process tree.
- Un identificador fuerte del activo (`DeviceId`, `AccountObjectId`, `RecipientEmailAddress`...): habilita el mapeo automático de la entidad.
- El identificador de la entidad sobre la que actuar, si quieres acción automática: sin él, la acción no sabe a quién aislar o deshabilitar.
- `SentinelScope_CF`, si hay `Sentinel scoping` configurado: sin ella, la alerta nace sin scope e invisible para analistas con alcance limitado.

- [ ] Alerta, entidades y acciones

- `Alert details`: severidad y categoría; título y descripción admiten nombres de columna entre dobles llaves, hasta tres por campo (`User {{AccountName}} unexpectedly signed in from {{Location}}`).
- Entity mapping: el asistente separa `Impacted assets` (cuenta, dispositivo, buzón, aplicación cloud, recursos de Azure/AWS/GCP) de `Related evidence` (todo lo demás). Solo se mapean como `Impacted assets` los tipos considerados activos, una columna por tipo, y solo si la consulta la devuelve. Ese mapeo es lo que después agrupa alertas en incidentes.
- Scope: todos los dispositivos o device groups concretos; limita qué consulta y sobre qué actúa. No afecta a reglas que solo miran buzones, usuarios o identidades.
- `Mark user as compromised`: exige `AccountObjectId`, `InitiatingProcessAccountObjectId` o `RecipientObjectId`; no vale `AccountUpn`, aunque sí sirva para el entity mapping general.
- `Disable user` y `Reset user authentication`: exigen el `Security Identifier (SID)` en `AccountSid`, `InitiatingProcessAccountSid`, `RequestAccountSid` u `OnPremSid`.
- Identidades de `Microsoft Entra`: la consulta debe devolver además `AccountObjectId` para cualquier acción sobre ellas.
- `Move to mailbox folder` (mueve a `Junk`, `Inbox` o `Deleted items`) y `Delete email` (`Soft delete` o `Hard delete`): ambas exigen `NetworkMessageId` y `RecipientEmailAddress`.

## Lo que no alerta aunque lo parezca

- `Microsoft security`: no lleva consulta ni mira raw events; toma alertas de otros productos Microsoft, filtradas por servicio y severidad (`Include`/`Exclude specific alerts` por texto), y crea con ellas incidentes de Sentinel. No disponible con `XDR incident integration` ni con Sentinel incorporado al portal de Defender, por la misma razón que `Fusion`.
- `Anomaly`: escribe en `Anomalies`, nunca alerta sola. `UEBA anomalies` comparan cada entidad con su historia, sus peers y la organización; las ML anomaly rules customizables entrenan 7-21 días. Publica como mucho las 3.000 mejores por score. Se ajusta duplicando la regla (nace en `Flighting`); al convencer, pasa a `Production` y la original cae a `Flighting`.
- Dos scores distintos: `InvestigationPriority` (`BehaviorAnalytics`, `0-10`) mide desviación de la línea base; `AnomalyScore` (`Anomalies`) mide intensidad del patrón. Uno alto no implica el otro.
- `UEBA` (`User and Entity Behavior Analytics`): aporta contexto de riesgo por entidad derivado de logs y alertas ya en `Analytics tier`, sin telemetría propia ni periodo fijo de aprendizaje. No es un conector ni alerta por sí sola: alimenta las `UEBA anomalies` y aporta `InvestigationPriority` en `BehaviorAnalytics`.
- `Advanced Hunting`: superficie de consulta, no motor de alerta. Solo se automatiza guardándola como `Custom detection rule` o regla analítica.
## Anatomía, supresión y cobertura de la alerta

La severidad no mide lo mismo según quién la ponga: la de `Microsoft Defender Antivirus` es la peligrosidad absoluta de la amenaza para ese dispositivo; la de `Microsoft Defender for Endpoint` es el riesgo del comportamiento, sobre todo para la organización. Una amenaza detenida antes de infectar sale `Informational`; un malware que llegó a ejecutarse pero fue bloqueado y remediado, sin amenaza para la organización, sale `Low`; si puede amenazar a la organización, `Medium` o `High` aunque acabara bloqueado.

- [ ] Construcción de una alerta

- `Entity mapping`: le dices a la regla qué columna de tu consulta es una IP, una cuenta, un host... Da igual cómo se llame la columna en cada tabla (`CIp` en una, `IpAddress` en otra): las dos quedan como la misma entidad `IP`. Límites: 10 mappings por regla, 3 identificadores por mapping y 500 entidades por alerta; lo que pase de ahí se descarta.
  Para qué sirve en realidad, más allá de nombrar la columna:
	- Correlación: dos alertas que comparten la misma entidad (misma IP, misma cuenta, mismo host) se agrupan en el mismo incidente. Sin el mapping, Defender XDR/Sentinel no sabe que hablan del mismo actor, aunque sea obvio para un analista.
	  - Acciones de respuesta: `Mark user as compromised`, `Isolate device`, `Move to mailbox folder`... actúan sobre una entidad. Si la columna no está mapeada como la entidad correcta, la acción no tiene sobre qué ejecutarse.
	  - Entity page: la ficha de investigación de un dispositivo/usuario/IP se arma juntando todo lo mapeado a esa entidad a través de distintas alertas.
	  - Grafo de investigación del incidente (qué tocó a qué), no solo la lista plana de alertas. Sin entity mapping hay una lista de alertas sueltas con texto libre; con entity mapping hay un grafo de entidades que se correlaciona y sobre el que se puede actuar.
- `Custom details`: No crean entidades ni sirven para correlacionar; eso lo hace el entity mapping. Límites: en Sentinel, 20 detalles y 2 KB por alerta; en una custom detection, 20 pares y 4 KB, y si te pasas se pierden todos, no solo lo que sobra.
- `Alert details`: título, descripción o severidad que cambian según los datos de la consulta, por ejemplo "Usuario {{AccountName}} inició sesión desde {{Location}}". Cada campo admite hasta 50 valores; si te pasas, ese campo pierde la personalización. Con Sentinel en el portal de Defender no cambies `ProductName` en alertas de productos Microsoft: Defender XDR podría descartar la alerta y no crear el incidente.
- `Event grouping`: decide si una ejecución da una sola alerta que resume todos los resultados (`Group all events into a single alert`) o una alerta por resultado (`Trigger an alert for each event`). En el segundo caso el tope es 150 en `Scheduled` y 30 en `NRT` (alertas por ejecución); si se supera, salen 149 (o 29) individuales y una última que resume el resto.

## Quién correlaciona

Hay dos motores de correlación. Sin onboarding pueden coexistir: Sentinel clásico correlaciona lo que llega a su workspace y XDR correlaciona por separado las alertas de sus workloads. Al incorporar el workspace primario al portal de Defender, el motor XDR pasa a gobernar la correlación de las alertas de Sentinel que participan en la experiencia unificada; los workspaces secundarios quedan fuera — sus alertas no se correlacionan con las de Defender ni con las de otros workspaces de Sentinel.

| Comportamiento                                             | Workspace sin incorporar al portal de Defender                                                                                                                                   | Workspace primario incorporado al portal de Defender                                                                                                                                         |
| ---------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Alcance de la correlación                                  | Sentinel clásico agrupa sus alertas; XDR sigue correlacionando por separado las alertas nativas de sus workloads                                                                 | XDR correlaciona las alertas participantes de Sentinel junto con las de los productos integrados                                                                                             |
| Motor que gobierna los incidentes de Sentinel              | `Incident settings` y `Alert grouping`; `Fusion` está disponible mientras no esté habilitada `Microsoft Defender XDR incident integration`                                       | Correlación unificada de `Microsoft Defender XDR`; `Fusion` queda deshabilitado                                                                                                              |
| Alertas de una regla con `Incident creation` deshabilitado | Permanecen como alertas sin incidente                                                                                                                                            | No aparecen en el portal de Defender                                                                                                                                                         |
| `Microsoft security incident creation rules`               | Convierten alertas de productos Microsoft en incidentes mientras no esté habilitada `Microsoft Defender XDR incident integration`                                                | Se deshabilitan para evitar duplicados                                                                                                                                                       |
| Reapertura por agrupación de una regla                     | Disponible                                                                                                                                                                       | No disponible; una alerta posterior crea otro incidente                                                                                                                                      |
| Conector y sincronización                                  | El conector XDR puede sincronizar alertas e incidentes, pero no convierte ambos motores en uno                                                                                   | El portal de Azure recibe la representación sincronizada; no ejecuta un segundo motor de correlación                                                                                         |
| Participación de reglas Sentinel en correlación XDR        | No aplica                                                                                                                                                                        | Por defecto ninguna participa; se suman con `#INC_CORR#` (o todas menos `#DONT_CORR#`, según `Incident correlation default setting` del tenant)                                              |
| Migración al onboarding                                    | No aplica                                                                                                                                                                        | Opcional: `Retain Sentinel incident creation behavior for XDR alerts` copia la agrupación existente a reglas de `Alert grouping` de Defender — migración puntual, no se resincroniza después |
| Título del incidente con título dinámico                   | Usa el título de la primera alerta                                                                                                                                               | Usa la táctica MITRE común a todas (puede no coincidir con el nombre en Sentinel)                                                                                                            |
| Reflejo del incidente en Sentinel                          | No aplica                                                                                                                                                                        | UI/API en <5 min; `Product name = Microsoft Defender XDR`; fila en `SecurityIncident` puede tardar más                                                                                       |
| Tope de alertas por incidente                              | 150 (`Alert grouping`)                                                                                                                                                           | XDR admite >150; Sentinel muestra `150+` con link al incidente completo en Defender                                                                                                          |
| Ciclo de vida del incidente                                | `New` → `Active` → `Closed`                                                                                                                                                      | `Active` → `In progress` → `Resolved`; resolver también resuelve las alertas activas vinculadas                                                                                              |
| Cuándo se clasifica                                        | Obligatorio recién al cerrar                                                                                                                                                     | En cualquier momento de la investigación                                                                                                                                                     |
| Vocabulario de cierre                                      | `True Positive - Suspicious activity`, `Benign Positive - Suspicious but expected`, `False Positive - Incorrect alert logic`, `False Positive - Inaccurate data`, `Undetermined` | `True positive`, `Informational, expected activity`, `False positive` — la sincronización transforma los campos compatibles entre los dos vocabularios                                       |

> La columna dice "workspace incorporado" porque esa es la condición que dispara el cambio, pero quien gobierna la correlación a partir de ahí es `XDR`, no el workspace — el workspace solo aporta las alertas que participan. Por eso un incidente creado a mano en Sentinel (portal de Azure, API, o playbook de Logic Apps), al no nacer de una alerta, nunca entra a esa correlación: sigue viéndose solo en Azure, Logic Apps y la API de Sentinel, y no aparece en el portal de Defender.

- `#INC_CORR#` y `#DONT_CORR#` son los tags que se escriben al principio de la descripción de una `analytics rule` de `Sentinel` para decidir si sus alertas entran o no a la correlación de `Defender XDR`, por encima del comportamiento por defecto del tenant. El toggle de tenant `Incident correlation default setting` viene apagado de fábrica: con eso apagado, ninguna regla participa salvo que lleve `#INC_CORR#` al principio de su descripción, que la suma explícitamente. Si en cambio ese toggle está encendido, es al revés: todas las reglas participan salvo las que lleven `#DONT_CORR#`, que las excluye. Una regla sin ninguno de los dos tags simplemente sigue el default del tenant. El tag no distingue mayúsculas, admite cualquier espaciado (o ninguno) después de él, y tiene que ir literalmente al principio del campo de descripción para que cuente. Cambiar el tag no afecta a las alertas ya creadas: cada alerta recibe su estado de correlación en el momento en que nace, y ese estado queda fijo.
- `Alert grouping`: en `Enabled` permite reunir varias alertas en un mismo incidente y en `Disabled`, cada alerta genera un incidente independiente. Criterios de agrupación abajo.
	- Ventana de agrupación: desde la primera alerta que abre el incidente, cualquier alerta que cumpla el criterio y llegue dentro de ese plazo se suma al mismo incidente; configurable de `5 minutos` a `7 días`, por defecto `5 horas`
	- Entidades y detalles seleccionados coinciden: compara las entidades, `Alert details` o `Custom details` elegidos; exige seleccionar al menos uno
- `Fusion` correlaciona dos o más alertas, actividades o anomalías y produce directamente un incidente multietapa de alta fidelidad en `SecurityIncident`, sin pasar por una alerta en `SecurityAlert`. Cada incidente `Fusion` admite como máximo 100 alertas o anomalías.
- En `Insider Risk Management`, el equivalente de estado es `Needs review` para `New`/`In progress`, y `Dismissed` para `Resolved` cuando no hay clasificación disponible; el equivalente de clasificación es `Confirmed` para `True positive`, o `Dismissed` para `Informational, expected activity` y `False positive`.
## El incidente ya formado

- [ ] Propiedades y ciclo de vida

| Propiedad            | Para qué sirve                                                                                                                                              |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Nombre y descripción | Resumen de la historia del ataque; XDR puede cambiar el nombre al correlacionar o fusionar                                                                  |
| Severidad            | `Informational` (sin riesgo relevante) · `Low` (riesgo bajo) · `Medium` (riesgo moderado) · `High` (riesgo alto/crítico para la organización ~ por defecto) |
| Propietario          | Un único usuario o grupo; en Defender la asignación se aplica también a sus alertas                                                                         |
| Etiquetas            | Clasifican, filtran y enrutan sin depender de un título que cambia                                                                                          |
| Determinación        | La subcategoría que explica esa conclusión: phishing, malware, cuenta comprometida, prueba de seguridad o aplicación empresarial                            |
| Comentarios y tareas | Conservan las decisiones y parten la investigación en pasos verificables                                                                                    |
- Nota sobre el vocabulario de cierre de Sentinel clásico: las dos razones de falso positivo separan regla mal escrita (`Incorrect alert logic`) de dato defectuoso (`Inaccurate data`); `Benign Positive` es actividad real pero esperada, no un fallo de la detección. 
- Cuando un incidente contiene alertas de `Insider Risk Management`, lo que se sincroniza entre Microsoft Defender y Purview es el estado y la clasificación de esas alertas, y cada portal usa un vocabulario distinto. Los cambios sobre una alerta se reflejan en ambos portales en un máximo de 30 minutos desde su generación o actualización, e incluyen estado, severidad, actividad que generó la alerta, información del desencadenante y clasificación

- [ ] Merge de incidentes

Correlación = asignar alerta a incidente (nuevo o existente) + seguir vigilando y fusionar incidentes si corresponde. El merge es esa segunda parte, no algo aparte: cuando la correlación detecta que dos incidentes ya formados son el mismo ataque, los fusiona. Uno de los dos (`target`) absorbe todo el contenido del otro (`source`); Defender decide cuál es cuál. El `source` queda `Redirected` y cerrado, no desaparece. No fusiona automático si uno ya está `Closed`, tienen dueños distintos, clasificación distinta, o rompería un límite de entidades/device groups — ahí entra la fusión manual: se arregla el bloqueo y se fuerza la unión. `All associated incidents` no fusiona nada, solo amplía contexto.

- [ ] Case management

- Existen dos tipos de `case`. `Incident case` *(preview)* envuelve un único incidente existente (relación 1:1, no agrupa varios). `Generic case` es para trabajo de SecOps que no está atado a un único incidente, y admite vincular incidentes, indicadores y recomendaciones como `linked objects`.
- Cambiar estado, clasificación o determinación en el `incident case` se sincroniza con el incidente relacionado, pero **no** resuelve sus alertas: las alertas mantienen su propio estado aunque el `incident case` se resuelva o cierre. Esto es distinto de lo que pasa al resolver un incidente clásico de Defender, que sí resuelve todas sus alertas activas vinculadas.
- `Incident case` es hoy la experiencia recomendada para gestionar incidentes; la experiencia clásica (descrita arriba en `El incidente ya formado`) sigue disponible mientras dure el preview.
# 9 · Investigación

El incidente ya está formado y asignado, y toca entenderlo: quién entró, por dónde, qué tocó y hasta dónde llegó. El capítulo sigue el orden en que se investiga: la cola, el incidente, sus alertas, sus entidades, la superficie del producto que las vio y, al final, el alcance. Aquí casi todo es lectura — la única excepción es recolectar evidencia (live response, investigation package)

  - `Collect investigation package`: descarga natural a un zip con el estado del dispositivo en ese momento — carpetas como Autoruns, Installed programs, Network connections, Prefetch files, Processes y Scheduled tasks. Sirve para identificar el estado actual del dispositivo y entender herramientas y técnicas del atacante, sin cambiar nada en él.
  - `Initiate live response session`: acceso remoto instantáneo al dispositivo por shell. Permite recolectar datos forenses, correr scripts, enviar entidades sospechosas a analizar, y también corregir amenazas y buscar amenazas emergentes en tiempo real.

> Live response sí puede usarse para remediar (correr scripts, arreglar) pero su función central acá es investigativa.

> El incidente se abre en `security.microsoft.com > Investigation & response > Incidents & alerts > Incidents`, y distribuye la investigación en pestañas. La columna derecha suma `Priority assessment`: puntuación de prioridad y los `Notable priority factors` que la explican (disrupción, tipos de alerta, etiquetas críticas, tácticas MITRE), lo de `alerts` ahí solo se ve las alertas ya generadas por el SOC o por motores nativos

``` 
Incident (legacy incident experience — Incident case ya es la recomendada, pero esta sigue vigente)
└── Pestañas del incidente
    ├── Attack story → incident graph (reproducible cronológicamente) + alert page
    │                → Go hunt (Advanced Hunting sobre la entidad seleccionada)
    │                → Blast radius (rutas de propagación)
    ├── Alerts → severidad, entidades, origen (Service source), por qué se enlazaron
    ├── Activities → timeline de acciones manuales/automáticas, filtrable por performed by/policy status
    ├── Assets → Devices · Users · Mailboxes · Apps · Cloud resources

    ├── Evidence and Response → veredicto (Malicious/Suspicious/Clean) + estado de remediación
    ├── Summary → alertas y categorías (kill chain/MITRE), scope, evidencia, incident information
    └── Similar incidents → otros incidentes con alertas/entidades/propiedades parecidas
                                ↓
                    el incidente deja de responder → se pivota por la entidad
```

## 1. El incidente como punto de partida

- [ ] Pestañas del incidente:

> `Attack story` reúne la historia multidominio en un solo lugar, pero no hay una superficie única que profundice en cada producto: para eso se usan las anteriores en orden.

- `Attack story`: alert page (what happened, actions taken, related events) + `incident graph`, que conecta entidades con sus assets y se puede reproducir cronológicamente. Incluye `Go hunt` (lanza Advanced Hunting sobre la entidad seleccionada) y `Blast radius` (rutas de propagación posibles desde un nodo hacia objetivos críticos), Learn dice "hasta siete saltos" como límite general, pero el máximo real depende del entorno: 5 en cloud, 5 on-premises, 3 en híbrido
- `Alerts`: cola de alertas del incidente — severidad, entidades, origen (`Service source`) y por qué se enlazaron.
	- `Process tree`: relación padre-hijo de los procesos de la alerta, con línea de comandos — navegable hacia entity pages.
	- `Alert timeline`: vista cronológica condensada, complementa al Process tree.
	- `Alert story`: por qué se disparó la alerta — eventos antes/después y entidades relacionadas, también navegable.
- `Activities`: Es la cronología de lo que ha pasado dentro del incidente, tanto acciones manuales y automáticas como eventos de correlación del tipo `Alert link` con categoría `Correlations`. Cada fila trae `Type`, `Category`, `Target`, `Performed by`, `Trigger` y `Activity status`, y el filtro `Origin: This incident` acota a lo ocurrido en este incidente.
- `Assets`: Devices, Users, Mailboxes, Apps, Cloud resources — vista unificada de todo lo afectado.
    - `Device timeline`:  cronología de eventos observados en el dispositivo; muestra los últimos 30 días inicialmente y retiene eventos por 90 días por defecto. `Hunt for related events` salta a Advanced Hunting desde un evento puntual. `Flagged events`: marcas y después filtras para armar la cronología limpia de la brecha.
- `Investigations`: investigaciones automatizadas de MDO (`AIR`) asociadas al incidente, con su veredicto.
- `Evidence and Response` (pestaña del incidente) ya da un primer vistazo por entidad: veredicto (Malicious/Suspicious/Clean) y estado de remediación, con la aprobación de acciones pendientes ahí mismo. Si hace falta profundizar en una entidad puntual, ahí mismo o desde una alerta, la barra de búsqueda global, o un resultado de `Advanced Hunting` se abre su `entity page` propia: `File` con metadatos, veredicto de Antivirus y ratio VirusTotal; `IP address` con reputación, ASN y `Observed in organization` (tope 100 dispositivos); `URL`/`Domain` con veredicto de Microsoft y clics observados, agrupado por FQDN aunque cada subdominio tenga página propia (con Sentinel se suma `Insights`).
- `Summary`: alertas y categorías (kill chain/MITRE), scope, evidencia, e incident information (tags, estado, severidad).

- [ ] Cuándo pivotar

- El incidente deja de responder → se sale por la entidad. Sus pestañas dicen qué entidades están implicadas y qué vio cada motor, pero no lo que esas entidades hicieron fuera de lo que alertó — para eso se entra en el inventario, en la superficie del producto que la vio o en la actividad de Microsoft 365.
## 2. Pivote por entidad (cuando el incidente no alcanza)

Los inventarios consolidan el contexto, las alertas, los incidentes y las acciones de cada activo, y permiten abrir la investigación por el activo afectado en vez de por el incidente. Bajo `security.microsoft.com` → `Assets` hay cinco:

- `Device inventory`: fuente autoritativa de todos los dispositivos visibles para Microsoft Defender for Endpoint — incorporados con agente y descubiertos en la red, no hace falta que tengan alertas para aparecer. Columnas clave: `Risk level` (riesgo de compromiso, sobre todo por alertas activas), `Exposure level` (por vulnerabilidades/recomendaciones pendientes, no por alertas), `Onboarding status` (`Onboarded`/`Can be onboarded`/`Unsupported`/`Insufficient info`), `Sensor health state` (`Inactive`/`Misconfigured`), `Criticality level`.
- `Identity inventory`: identidades de Active Directory y Microsoft Entra ID en una sola vista.
- `Applications`: las aplicaciones descubiertas y su uso.
- `Cloud`: los recursos cloud incorporados.
- `AI agents`: los agentes de IA del tenant.

`Service source` (qué producto entregó la alerta) dice cuál de estas filas usar. `Detection source` (qué motor la produjo dentro de ese producto) no cambia la fila — cambia cuánto se confía en la alerta y cómo se ajusta después. Los valores no son universales, cada producto tiene los suyos:

| Sentinel            | `security.microsoft.com > Investigation & response > Incidents`                  | Incidentes, alertas, entidades, Attack story                                          | Analytics Rules: Scheduled / NRT                                                                                        |

## 5. Alertas de IRM y DLP (motores que ya decidieron, no consultas)

Esta capa reúne alertas que ya vienen resueltas por el motor de políticas, no señales crudas para triar desde cero — el analista de `SC-200` investiga el contexto de la decisión, no ajusta la política (eso es `SC-401`).

| Motor                     | Unidad de investigación                | Dónde se encuentra                                                                                  | Pestañas / detalle clave                                                                                                                                                                   |

## 6. Security Copilot (capa transversal, no un paso más)

- Las capacidades interactivas respetan los permisos del usuario mediante `on behalf of (OBO)`; esto no significa que todo Copilot sea de solo lectura. Sus agentes pueden ejecutar acciones con su identidad y permisos, como resolver alertas falsas positivas. Exige capacidad de Security Copilot provisionada y los roles/permisos correspondientes; las restricciones de plugins también se aplican.
- El par que más se confunde: `Incident summary` (cuenta el ataque — cuándo empezó, en qué activo, línea temporal, IOCs, actores; tope de 100 alertas, límite propio, no relacionado con el máximo de Fusion) vs `Incident report` (cuenta la gestión — analistas, clasificación, acciones, playbooks).
- Dos agentes con identidad y permisos propios, no heredan acceso a todo:
	- `Phishing Triage Agent`: triaga correos reportados por usuarios, veredicto `True Positive` (deja el incidente para el analista) o `False Positive` (resuelve la alerta).
	- `Identity Risk Management Agent`: investiga usuarios `At risk` en Entra ID Protection, veredicto `Compromised`/`Not compromised`, propone `Dismiss risk` o `Reset password`.
- En `Risky users` de Entra ID Protection conviven dos salidas de Copilot que no son lo mismo: `Risky user summarization` (capacidad embebida — resume y recomienda, pero NO emite veredicto) vs el `Identity Risk Management Agent` de arriba (sí dictamina). Si el agente está activado, Learn avisa que vas a ver las dos por separado en la misma vista.
- `Copilot en Microsoft Intune` (experiencia embebida): al crear una policy y añadir un setting aparece un tooltip de Copilot; desde él se pregunta si el setting ya está configurado en otras policies, qué valor recomienda Microsoft y cómo afecta a usuarios y a seguridad. Vale para compliance policies, device configuration (settings catalog incluido) y la mayoría de endpoint security policies; sobre una policy existente está `Summarize with Copilot`. No tiene licencia propia: consume SCUs de Security Copilot. [Learn: Copilot en Intune](https://learn.microsoft.com/en-us/intune/copilot/)
- No lo reemplaza nada: ni onboardear Sentinel, ni una automation rule, ni AIR. El `Dynamic Threat Detection Agent` es otra cosa aparte (genera alertas propias, vive en Detección y alertas).
# 10 · Hunting 

El hunting parte de una hipótesis; no requiere una alerta previa, aunque puede ampliar una investigación existente. El capítulo se organiza en tres apartados: formular la hipótesis; elegir la superficie y la vía para conservar o repetir los hallazgos; y consultar, interpretar y ampliar.

## 1 · Formular la pregunta o hipótesis

El hunting parte de una pregunta o hipótesis para buscar amenazas que no generaron una alerta. Puede iniciarse antes de un incidente, ampliar una investigación en curso o aplicarse después para mejorar las detecciones. Hay cuatro orígenes.

| Origen                                                  | Dónde                                                                              | Qué aporta                                                                                                                                                                            |
| ------------------------------------------------------- | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Un incidente, alerta o entidad                          | `Go hunt` / `Hunt for related events` (MDE)                                        | Abre `Advanced Hunting` con la consulta ya armada sobre esa entidad o evento                                                                                                          |
| `Threat Analytics` — es Microsoft diciéndote qué buscar | `security.microsoft.com` > `Threat Intelligence` > `Threat analytics` > el informe | `Analyst report`, `Impacted assets`, `Endpoints exposure`, `Recommended actions`, `Indicators` *(preview)*, `Overview`, `Related incidents` = catálogo por defecto de microsoft       |
| `MITRE ATT&CK` y `Content hub`                          | `Microsoft Sentinel` > `Threat management` > `MITRE ATT&CK` / `Content hub`        | Técnicas sin cubrir según las reglas activas/simuladas en tu workspace  / Catálogo curado de Microsoft/partners: consultas, reglas y soluciones listas para desplegar                 |
| `Hunts` *(preview)*                                     | `Microsoft Sentinel` > `Threat management` > `Hunting` > `Hunts`                   | Flujo completo de threat hunting en Sentinel: hipótesis → consultas KQL → investigar resultados/bookmarks → validar o descartar → crear detecciones/incidentes/TI si encuentras algo. |

- `Threat Analytics`, detalle de las 7 secciones: `Analyst report` (análisis escrito, cadena de ataque, hunting queries, mitigaciones no rastreadas dinámicamente), `Impacted assets` (detección real, por devices/users/mailboxes/apps/cloud resources), `Endpoints exposure` (vulnerables o mal configurados aunque no haya pasado nada), `Recommended actions` (solo lo rastreado en `Microsoft Secure Score`; el resto vive en el `Analyst report`), `Indicators` *(preview, los IOC de la amenaza incluidos los expirados, exige tenant verificado)*, `Overview` y `Related incidents`.
- Categorías del informe: `Activity`, `Actor`, `Core threat`, `Technique`, `Tool`, `Vulnerability`, `OSINT` *(preview)*. En `OSINT` las pestañas que dependen del entorno pueden venir vacías.
- Permisos: `Security data basics (read)` para informe/incidentes/activos; exposición y acciones recomendadas exigen además `Vulnerability management (read)` y `Exposure Management (read)`. `MDE P1` no da acceso por sí solo. Clientes de Sentinel SIEM tienen acceso limitado a ciertas secciones.
- `Threat Intelligence Briefing Agent`: agente de Security Copilot embebido en `Threat analytics`, prioriza informes cruzando actividad de actores con la exposición real de la organización. Exige capacidad de Security Copilot.

## 2 · Elegir la superficie, conservar el hallazgo y decidir si debe repetirse

| Superficie                             | Dónde                                                                                            | Qué consulta                                                                                                         | Cómo conservar o escalar el hallazgo                                                                                                    | Condiciones                                                                                                                                                                                                                                                                                                                         | Si debe repetirse                                                                                                                                                                                                                                             |

> Si el hallazgo revela una entidad activamente comprometida, la respuesta no espera a esta decisión: se actúa de inmediato sobre esa entidad (desde el incidente vinculado, si el resultado ya se subió con `Link to incident` o un `bookmark`, o directamente desde la entidad si viene de `Go hunt`).

- Una consulta de `Advanced Hunting` devuelve como máximo 100.000 filas o 64 MB y puede ejecutarse hasta 10 minutos. Hay además una cuota de CPU (Central Processing Unit) por tenant: el portal avisa al superar el 10% de la porción de recursos asignada, y bloquea las consultas si se llega al 100%, hasta el siguiente ciclo de 15 minutos o el ciclo diario, según cuál se haya agotado. Las consultas se escriben siempre en UTC (Coordinated Universal Time); los resultados se muestran en el timezone configurado del portal.
- La frescura depende del tipo de tabla, no del workload: las de evento (`DeviceProcessEvents`) llegan casi en tiempo real; las de entidad (`DeviceInfo`, `IdentityInfo`, `OAuthAppInfo`) describen estado y pueden tener varias filas por entidad, cada una con su propia regla de actualización (`IdentityInfo`: por cambio o cada 24 horas, sin regla universal). MDO no tiene una tabla de entidad consolidada; sus tablas `*Info` contienen metadatos asociados a mensajes, no un resumen persistente de una entidad.
- En el data lake las cuotas son otras y se cuentan por tenant, no por usuario, y la documentación indica una latencia de 15 minutos hasta que el dato recién ingerido queda consultable ahí — a tener en cuenta al programar jobs con ventanas cortas.

### Workbooks

`Workbooks`: paneles visuales interactivos (gráficos, tablas, mapas) armados sobre consultas `KQL`, para monitorear tendencias y patrones de forma continua — no para una investigación puntual. Sirven para reportar postura de seguridad, seguir el volumen de una fuente de datos, o dar seguimiento visual a una amenaza específica a lo largo del tiempo. Como guarda el `JSON` del layout (no los datos), siempre lee la telemetría en vivo cada vez que se abre.
### Servidor MCP de Sentinel

Servidor de herramientas de seguridad alojado por Microsoft, consultable en lenguaje natural, autenticado con Entra ID y limitado a los permisos de la identidad que lo usa. No vive en el portal de Defender ni en `Data lake exploration`: se agrega desde un cliente compatible (VS Code, Security Copilot, Copilot Studio, Foundry) y se usa desde el chat de ese cliente, en modo agente — no es una librería que se importe dentro del notebook. Colecciones principales: `Data exploration`, `Triage` y `Security Copilot agent creation`.

# 11 · Respuesta y remediación

La respuesta transforma la evidencia en acciones sobre los activos afectados. El recorrido termina cuando se comprueba la remediación y se recupera el servicio de forma segura.

```text
1 · Ejecutar la acción sobre el activo
    dispositivo · fichero · identidad · correo · app · recurso cloud · datos
                              ↓
2 · Si la acción estándar no basta → Live response para remediar
                              ↓
3 · Comprobar ejecución y aprobar lo pendiente
    Action center · registro del producto correspondiente
                              ↓
4 · Verificar que el activo es seguro → revertir contención y recuperar
```

Con evidencia suficiente, se actúa sobre el activo afectado aunque la investigación siga abierta. Contener limita el ataque; remediar elimina la amenaza y su persistencia; recuperar devuelve el activo al servicio. Aislar un equipo no demuestra que esté limpio.

## 1 · Ejecutar la acción sobre el activo

### Dispositivo · MDE

En Defender: `Assets` > `Devices` > dispositivo > barra de acciones.

| Acción | Cuándo elegirla y qué hace | Recuperación |
| --- | --- | --- |
| `Isolate device` | Equipo incorporado comprometido: restringe su red y mantiene el canal con MDE | `Release from isolation` |
| `Contain device` | Dispositivo no administrado sospechoso: los endpoints compatibles incorporados a MDE bloquean su comunicación con él | `Release from containment` |
| `Restrict app execution` | Impedir ejecuciones: permite archivos firmados por Microsoft | `Remove app restrictions` |
| `Run antivirus scan` | Buscar y remediar malware mediante análisis rápido o completo; admite Defender Antivirus en modo `Passive` | Comprobar el resultado del análisis |

- `Contain` protege mediante los equipos vecinos; no instala un agente ni limpia el dispositivo contenido. Learn recomienda hasta 100 dispositivos contenidos simultáneamente. El aislamiento se levanta automáticamente a los siete días; eso no certifica la remediación. La disponibilidad depende de plataforma, licencia, permisos y restricciones del activo. [Learn: dispositivos](https://learn.microsoft.com/en-us/defender-endpoint/respond-machine-alerts).
- Cambio vigente: desde el 1/09/2026, AIR de MDE no admite inicio manual como investigación separada; para comprobaciones bajo demanda, Learn indica un análisis antivirus completo. Este cambio no afecta al AIR de MDO. [Learn: AIR de MDE](https://learn.microsoft.com/en-us/defender-endpoint/automated-investigations).

### Fichero · MDE

Desde la página del fichero, accesible desde una alerta, evidencia o búsqueda.

| Necesidad | Acción y efecto |
| --- | --- |
| Detener malware ya observado | `Stop and quarantine file`: detiene procesos, pone el archivo en cuarentena y elimina persistencia, como claves de registro |
| Impedir futuras ejecuciones | Indicador de bloqueo del archivo; la cuarentena puntual no sustituye ese control persistente |
| Recuperar un falso positivo | Restaurar en cada dispositivo con `MpCmdRun.exe -Restore`, seleccionando el elemento adecuado |

- `Stop and quarantine` exige Defender Antivirus al menos en `Passive` y un Windows compatible; excluye archivos firmados por Microsoft o de editores de confianza. Actúa donde el archivo se observó en los últimos 30 días, con un máximo de 1.000 dispositivos.
- Los tres días son el timeout de entrega de la acción: si el equipo sigue desconectado, no la recibe. No significa que la cuarentena dure tres días. Comprobar `Success`, `Failed` y `Pending` por dispositivo. Restaurar exige haber confirmado que el archivo es legítimo. [Learn: archivos](https://learn.microsoft.com/en-us/defender-endpoint/respond-file-alerts).

### Identidad · Entra ID Protection y MDI

Desde la identidad en Defender > `Actions`, o desde `Risky users` / `Risky sign-ins` en Entra ID Protection.

| Situación | Respuesta |
| --- | --- |
| Cuenta comprometida | Deshabilitar o bloquear acceso, revocar sesiones y cambiar credenciales según el caso; confirmar el compromiso |
| Riesgo de inicio de sesión | MFA puede remediar el riesgo de esa autenticación |
| Riesgo de usuario con contraseña | Cambio seguro de contraseña o restablecimiento administrativo; verificar el estado de riesgo resultante |
| Falso positivo validado | Descartar el riesgo; esta acción no cambia la contraseña |
| Usuario legítimo bloqueado | Identificar la causa, remediar el riesgo y comprobar el acceso; no desactivar políticas como respuesta habitual |

- `Dismiss risk` (descartar) y remediar no son equivalentes: descartar cambia el estado del riesgo, pero no neutraliza credenciales robadas. [Learn: remediar riesgos](https://learn.microsoft.com/en-us/entra/id-protection/howto-identity-protection-remediate-unblock).
- Modelo de estados de riesgo: `At risk` es el punto de partida. Pasa a `Remediated` con MFA (riesgo de inicio de sesión), con un cambio seguro de contraseña, o con una contraseña temporal generada por el administrador (`Reset password`). Pasa a `Dismissed` con `Dismiss risk` o automáticamente si el sistema reevalúa el inicio de sesión como seguro. Pasa a `Confirmed compromised` solo con la acción explícita `Confirm compromised` en el portal — deshabilitar la cuenta, revocar refresh tokens, deshabilitar dispositivos o revocar access tokens vía CAE son pasos de contención que se hacen aparte, no los que cambian el estado. [Learn: remediar riesgos](https://learn.microsoft.com/en-us/entra/id-protection/howto-identity-protection-remediate-unblock).
- Deshabilitar y revocar tampoco son equivalentes: bloquear la cuenta impide obtener nuevo acceso; revocar refresh tokens no garantiza que todos los access tokens y sesiones de aplicaciones terminen inmediatamente. CAE acelera la invalidación en aplicaciones compatibles; las sesiones propias de una aplicación requieren su mecanismo de revocación. En identidades híbridas, actuar también sobre el origen de Active Directory. [Learn: revocar acceso](https://learn.microsoft.com/en-us/entra/identity/users/users-revoke-access).
- MDI permite `Disable`, `Enable`, `Revoke session`, `Mark as compromised` y `Force password change` (solo en Active Directory y Entra ID) [Learn: acciones de identidad](https://learn.microsoft.com/en-us/defender-for-identity/remediation-actions).

| ---------------------------- | ------------------------------------------------------------- |
| `Inspect resource context`   | Lleva a los activity logs del recurso que respaldan la alerta |
| `Mitigate the threat`        | Pasos manuales para remediar la amenaza sobre el recurso      |
| `Prevent future attacks`     | Recomendaciones para reducir la exposición futura             |
| `Trigger automated response` | Ejecuta una Logic App; la orquestación se configura aparte    |
| `Suppress similar alerts`    | Reduce alertas futuras similares; no elimina la amenaza       |

Aplicar la corrección al recurso y verificarla antes de dar la alerta por atendida. **Cambiar su estado no ejecuta la remediación.** [Learn: responder en MDC](https://learn.microsoft.com/en-us/azure/defender-for-cloud/manage-respond-alerts).

Ejemplo de Key Vault: ante acceso no autorizado, restringir el origen o retirar sus permisos; determinar qué secretos, claves o certificados fueron accedidos y rotarlos, deshabilitando los comprometidos. Reconocer al usuario o aplicación no demuestra que el acceso fuera legítimo. [Learn: respuesta en Key Vault](https://learn.microsoft.com/en-us/azure/defender-for-cloud/defender-for-key-vault-introduction).

Remediación de código con Security Copilot: ante malas configuraciones de infraestructura como código, la integración de `Defender for Cloud` con `Microsoft Security Copilot` genera automáticamente una pull request en el repositorio de `Azure DevOps`, partiendo de la recomendación `Azure DevOps repositories should have infrastructure as code scanning findings resolved`; un desarrollador la revisa y aprueba antes del merge. Requisitos en `# 1 · Licencia y onboarding > Por consumo > Microsoft Security Copilot`. [Learn: remediar código con Copilot](https://learn.microsoft.com/en-us/azure/defender-for-cloud/remediate-code-with-copilot)

## 2 · Live response para remediar

Defender > dispositivo > `Initiate live response session`, cuando las acciones estándar no bastan.

| Comando | Uso de respuesta |
| --- | --- |
| `remediate` | Elimina un archivo/entrada de registro/tarea; detiene procesos o servicios y elimina su ejecutable según el tipo |
| `run` | Ejecuta un script previamente cargado en la library |
| `putfile` | Copia al equipo un archivo de la library |

Ejemplo: `remediate file <ruta> -auto` ejecuta automáticamente el paso previo necesario. Revisar `Command log` para confirmar resultado.

Comandos: 10 minutos, excepto `getfile`, `findfile` y `run`, con 30. `Ctrl+C` cancela en el portal, pero no garantiza detener la operación en el agente. ## 4 · Verificar y recuperar

Antes de liberar: confirmar que la acción terminó, que la amenaza y su persistencia se trataron y que el activo puede volver al servicio. Si sigue comprometido, mantener o ajustar la contención.

Usar la reversión correspondiente: liberar aislamiento/contención, retirar restricciones, restaurar un archivo legítimo o habilitar una cuenta ya asegurada. Esto también aplica cuando la contención la inició Automatic attack disruption: la automatización no sustituye la comprobación posterior del analista.

# 12 · Automatización

Automatizar es definir qué inicia una respuesta, sobre qué alcance actúa y qué pasos ejecuta sin repetirlos manualmente. Puede investigar, contener, enriquecer, actualizar incidentes o notificar; no se limita a ataques que la organización ya haya visto.

```text
señal o cambio
   ├── protección nativa → ZAP · AIR · attack disruption
   └── proceso del SOC → automation rule · workflow automation
                           ↓
              comprobar condiciones y alcance
                           ↓
   acción SOC · actualización directa · playbook
                           ↓
             ejecución automática o aprobación
                           ↓
       comprobar resultado → notificar → seguimiento en # 11
```

## 1 · Automatización nativa de Defender
### ZAP: protección después de la entrega

`Zero-hour auto purge` vuelve a evaluar correo ya entregado y actúa si resulta malicioso. En correo revisa las últimas 48 horas, conforme al veredicto y las políticas aplicables; funciona en buzones cloud, no en buzones locales. Distinción de examen: para spam solo actúa sobre mensajes no leídos; para malware, phishing y high confidence phishing actúa sobre leídos y no leídos. No necesita que el SOC apruebe una remediación AIR.
### AIR: investigación y remediación

Automated Investigation and Response `AIR` analiza las evidencias asociadas a alertas compatibles y determina la respuesta; aplica solo en `MDE` y `MDO`. Hay que distinguir el producto y su mecanismo de aprobación, que no es el mismo en los dos

> Cambio desde el 1 de septiembre de 2026: AIR de MDE deja de ofrecer una investigación separada y el inicio manual; sus capacidades quedan integradas en la protección antivirus. Para comprobar un dispositivo bajo demanda se usa un análisis completo. AIR de MDO sigue disponible. [Learn: cambio en AIR](https://learn.microsoft.com/en-us/defender-xdr/m365d-autoir-results)

> `Full / Semi / No automated response` son una configuración que vive en el device group de MDE (Microsoft Defender for Endpoint) y que originalmente sirve para gobernar al AIR

| Nivel de MDE                                               | Cuándo automatiza sin pedir nada                   | Cuándo pide aprobación                             |
| ---------------------------------------------------------- | -------------------------------------------------- | -------------------------------------------------- |
| `Full - remediate threats automatically`                   | En cualquier carpeta; recomendado                  | Nunca                                              |
| `Semi - require approval for core folders remediation`     | En todo, salvo las carpetas del sistema            | Solo en carpetas del sistema                       |
| `Semi - require approval for non-temp folders remediation` | Solo en carpetas temporales                        | En todo lo demás, incluidas las del sistema        |
| `Semi - require approval for all folders`                  | Nunca — ninguna carpeta queda exenta               | Siempre, en cualquier carpeta                      |
| `No automated response`                                    | Nada — desactiva la investigación/respuesta de AIR | No aplica; no equivale a apagar toda la protección |

Se selecciona en `Settings > Endpoints > Permissions > Device groups`, al crear o editar el grupo. En los niveles `Semi`, las acciones pendientes caducan a los **7 días** y una acción caducada se comporta igual que una rechazada. [Learn: niveles](https://learn.microsoft.com/en-us/defender-endpoint/automation-levels) y [configuración](https://learn.microsoft.com/en-us/defender-endpoint/configure-automated-investigations-remediation).

MDO Plan 2: la remediación de AIR requiere aprobación por defecto. En `Settings > Email & collaboration > MDO automation settings` se puede autorizar `Soft delete` automático para clusters de archivos similares, URL similares o varios atributos comunes. Los clusters no seleccionados y los de más de 10.000 mensajes quedan pendientes. No se gobierna mediante device groups de MDE.

Para comprobar lo automatizado: `Action center > History`, filtro `Decided by = Automation`; en Threat Explorer, `Additional action = Automated remediation:automated`. La aprobación y reversión están en `# 11 > Action center`. [Learn: remediación automática en MDO](https://learn.microsoft.com/en-us/defender-office-365/air-auto-remediation).

### Automatic attack disruption

Automatic attack disruption es una función que, cuando detecta señales de mucha confianza de que hay un ataque en curso, actúa sola: aísla o corta el acceso de lo que está comprometido. No es un playbook que alguien escribe para cada caso, es lógica ya armada por Microsoft. El analista solo puede ajustar requisitos y excepciones, no redactar la respuesta.

Para que funcione en `MDE` es necesario revisar que el sensor esté activo, el nivel de descubrimiento de dispositivos y el device group: puntualmente, la acción `Contain device` solo se dispara si el descubrimiento está en modo `Standard discovery` (configuración de MDE), no alcanza con el modo básico. En `MDI` revisa que la auditoría esté prendida y que la cuenta de servicio tenga los permisos necesarios para actuar.

Un detalle importante: si `MDE` está configurado en nivel `Semi` (automatización semi-automática, que normalmente pide aprobación antes de actuar), eso no aplica acá, attack disruption puede contener el dispositivo igual, sin pedir aprobación previa. Y si a un device group se le puso la etiqueta `No automated response`, ese grupo queda afuera, no lo toca.

Predictive shielding es una extensión (todavía en preview) de esta misma idea, pero mirando hacia adelante: mientras el ataque sigue activo, protege lo que probablemente sea el próximo blanco, aunque ese activo todavía no esté comprometido. Puede contener usuarios o endurecer configuraciones (`GPO`, `Safeboot`) preventivamente.
## 2 · Reglas de automatización de Sentinel

Una `automation rule` es la capa que organiza la respuesta después de que algo ya fue detectado por una regla analítica (`Scheduled`, `NRT`, etc.): define trigger (cuándo se dispara, por ejemplo al crearse un incidente), condiciones y acciones (cambiar propietario, estado o severidad, agregar etiquetas o tareas, ejecutar un playbook), sin detectar nada por sí misma. El trigger estándar de alerta cubre reglas `Scheduled`, `NRT` y `Microsoft security`; no cubre directamente alertas XDR

| Trigger estándar | Uso |
| --- | --- |
| `When incident is created` | Clasificar, asignar o iniciar una respuesta al abrirse el incidente |
| `When incident is updated` | Reaccionar a cambios de estado, propietario, alertas o etiquetas |
| `When alert is created` | Responder a una alerta aunque no tenga incidente asociado |
Las `automation rules` de un mismo trigger corren en orden ascendente por número, y cada regla ve los cambios que dejó la anterior; si dos quedan empatadas en el mismo número, no hay garantía de cuál corre primero. `Updated by` sirve para evitar bucles, marcando quién hizo el último cambio y permitiendo cortar si fue la propia regla. Una regla con fecha de expiración se desactiva sola al llegar esa fecha. Y si el playbook que dispara la regla tarda más de dos minutos, la regla sigue de largo sin esperarlo, por eso cualquier paso que dependa de que el playbook termine debe ir dentro del propio playbook, no como acción separada después (Automation Rule → Playbook largo → dentro del playbook haces A → esperar → B → C)

- [ ] Extensiones en el portal de Defender

| Opción                     | Qué debes distinguir                                                                                                                                                                                                          |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Simple Flows` *(preview)* | Acciones predefinidas dentro del asistente: notificar creación/actualización de cases, añadir tareas o actualizar una alerta. No requiere construir una Logic App                                                             |
| `Enhanced Alert Trigger`   | Automatización de alertas de Sentinel y Defender/XDR; permite actualizar la alerta o ejecutar un playbook generado. Una acción por regla, sin orden de prioridad ni fechas de expiración; hasta 500 reglas activas por tenant |

Un **playbook generado** usa código Python e integration profiles para acceder a servicios; se revisa y valida antes de utilizarlo. Es una opción distinta del playbook tradicional basado en Azure Logic Apps. Nace deshabilitado y hay que activarlo; admite alertas o incident cases como entrada y no puede invocar a otro playbook. [Learn: Simple Flows](https://learn.microsoft.com/en-us/azure/sentinel/automation/create-basic-automation-rules-simple-flows) y [automatización en Defender](https://learn.microsoft.com/en-us/defender-xdr/siem-defender-automation).

## 3 · Playbooks y orquestación

- `automation rule` de Sentinel (trigger): `When incident is created`, `When incident is updated`, `When alert is created`
- `playbook` / Logic App (trigger): `Microsoft Sentinel incident`, `Microsoft Sentinel alert` y `Microsoft Sentinel entity`
- `Workflow automation` de Defender for Cloud (trigger): `When a Defender for Cloud Alert is created or triggered` (también existen el de recomendación y el de cumplimiento normativo)

Un `playbook` de `Azure Logic Apps` ejecuta un proceso con conectores, condiciones y acciones: enriquecer una IP, abrir un ticket, pedir aprobación o responder sobre un activo. No es una capa montada "encima" de `Azure Logic Apps`, como sí lo es `Microsoft Sentinel` sobre un `Log Analytics workspace`: un `playbook` es literalmente un recurso de `Azure Logic Apps`. `Azure Logic Apps` es un servicio genérico de automatización de Azure, usado para cualquier proceso, no solo de seguridad; cuando Sentinel lo conecta a una `automation rule` para responder a un incidente, a ese mismo recurso se lo llama "playbook". No hay dos capas separadas ahí: es el mismo recurso de Azure, con un nombre funcional distinto según el contexto en el que se usa.

1. Crear el playbook desde `Automation > Playbooks`, usando una plantilla disponible o un workflow propio.
2. Elegir el trigger compatible con el objeto que recibirá; para el flujo habitual de incidentes, usar `Microsoft Sentinel incident`.
3. Configurar conexiones y acciones; una plantilla desplegada necesita sus conexiones autorizadas.
4. Probarlo manualmente y revisar su ejecución.
5. Asociarlo a la automation rule y conceder a Sentinel permiso para ejecutarlo.

| Componente              | Qué hace                                                                        |
| ----------------------- | ------------------------------------------------------------------------------- |
| `Trigger`               | Inicia el workflow y determina el esquema recibido: incidente, alerta o entidad |
| `Action`                | Ejecuta cada operación posterior                                                |
| `Dynamic content`       | Reutiliza valores del trigger o de acciones anteriores                          |
| `Entities — Get <type>` | Extrae entidades del tipo necesario; su lista se recorre con `For each`         |

Cuando un playbook arranca desde un incidente, tiene acceso directo a las alertas y entidades de ese incidente. Si arranca desde una entidad suelta (por ejemplo, clickeando "`Run playbook`" sobre un dispositivo puntual), es un flujo manual centrado en ese activo, sin todo el contexto del incidente alrededor. Si en cambio el playbook necesita actualizar un incidente desde otro contexto (por ejemplo, uno que arrancó por una entidad y quiere tocar el incidente relacionado), necesita el `Incident ARM ID` para identificar cuál.

Sobre el tipo de Logic App: `Consumption` corre en un entorno compartido entre varios tenants (más simple, es lo típico). `Standard` corre aislado (single-tenant), permite meter varios workflows juntos y da más control de red, pero en Sentinel esos workflows Standard tienen que ser `stateful` (guardan el historial de ejecución paso a paso, no `stateless`). Cada conector que uses (Teams, Outlook, etc.) pide su propia autenticación; conviene usar una identidad administrada en vez de una cuenta personal, para no depender de que esa persona siga teniendo acceso.

Si un playbook no aparece para elegir o falla al correr, la checklist de causas es: que el trigger sea compatible, que esté seleccionada la suscripción correcta, que Sentinel tenga permisos para ejecutarlo, que las conexiones estén autenticadas, y que tenga acceso al recurso destino. Ojo con esto: que la ejecución haya arrancado NO significa que todas sus acciones internas hayan terminado bien, hay que revisar el detalle de la corrida. La forma vieja de disparar automatización desde una alerta, `Alert Automation (Classic)`, se retiró en marzo de 2026 — si hay enlaces viejos apuntando a eso, hay que reemplazarlos por `automation rules`.

`Workflow automation` de Defender for Cloud es el mismo concepto pero aplicado a ese producto: eliges la suscripción, el tipo de evento (alerta de seguridad, recomendación, o cambio en una evaluación de cumplimiento) y sus filtros, y lo asocias a una Logic App `Consumption`. Ejemplo: una alerta de severidad alta dispara esa Logic App, que dentro de sí misma crea un ticket y notifica al responsable.

El repositorio pasa a ser la fuente de verdad: un despliegue puede sobrescribir cambios del portal. Memoriza la diferencia entre desplegar la definición y ejecutarla cuando ocurre el trigger. Revisar el objeto que activó la automatización, el historial del motor y el resultado en el destino. En Defender, consultar `Action center` para las acciones compatibles; en Sentinel, la actividad del incidente; en Logic Apps, `Run history` y las entradas/salidas del paso fallido. Las notificaciones avisan; no ejecutan la remediación.

| Qué quieres recibir | Ruta desde `Settings` del portal de Defender |
| --- | --- |
| Incidentes | `Microsoft Defender XDR > Email notifications > Incidents` |
| Acciones de respuesta | `Microsoft Defender XDR > Email notifications > Actions` |
| Informes de amenazas | `Microsoft Defender XDR > Email notifications > Threat analytics` |
| Alertas de endpoint | `Endpoints > General > Email notifications` |

Crear la regla, seleccionar condiciones/alcance y destinatarios, enviar un correo de prueba y guardar. Para acciones de respuesta se filtra por origen manual/automático, acción, grupos de dispositivos y resultado completado/fallido; estas notificaciones no cubren las acciones de custom detections. ## 5 · Acciones

1. Elegir el motor: `AIR`, `attack disruption`, `automation rule`, `playbook` o `Workflow automation` de MDC (Microsoft Defender for Cloud).

## 5 · KQL que hay que manejar

Una consulta es una secuencia de statements separados por `;`, y todo `let` termina en punto y coma. Dentro de la expresión tabular, cada operador recibe por la pipe la salida del que tiene a su izquierda, así que el orden cambia tanto el resultado como el rendimiento

| Operador o función                                     | Para qué sirve                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| ------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `where`                                                | Filtrar filas; aplicar primero el tiempo y después la condición                                                                                                                                                                                                                                                                                                                                                                                       |
| `project`                                              | Elegir columnas de salida, renombrarlas y añadir calculadas; omitir una columna la retira del resultado, y limitar el resultado mejora el rendimiento<br>•  `project-away` : muestra todas menos las columnas que indiques.<br>•  `project-keep` : conserva solo las columnas que indiques, como  project .<br>•  `project-rename` : cambia nombres sin eliminar columnas.<br>•  `project-reorder` : cambia el orden de las columnas.                 |
| `extend`                                               | Calcula y añade columnas nuevas a cada fila; conserva las filas y columnas existentes                                                                                                                                                                                                                                                                                                                                                                 |
| `summarize`                                            | agrupa filas (con  `by`) y calcula agregados por grupo, como  `count()`  o  `sum()`. Sin  `by`, calcula un único resultado para todas las filas                                                                                                                                                                                                                                                                                                       |
| `count()`, `countif()`                                 | Cuenta filas de cada grupo, o solo las que cumplen una condición. Ej.: `summarize Total = count() by Categoria`.                                                                                                                                                                                                                                                                                                                                      |
| `dcount()`, `dcountif()`                               | Estima valores distintos; prioriza rendimiento y puede variar ligeramente. Ej.: `summarize Valores = dcount(Columna) by Categoria`.                                                                                                                                                                                                                                                                                                                   |
| `sum()`, `avg()`, `min()`, `max()` y variantes `*if()` | Calculan suma, media, mínimo o máximo por grupo. Las variantes `*if()` agregan solo filas que cumplen una condición.                                                                                                                                                                                                                                                                                                                                  |
| `bin()`                                                | Redondea hacia abajo al intervalo indicado; permite agrupar por tiempo. Ej.: `summarize Total = count() by bin(Timestamp, 1h)`.                                                                                                                                                                                                                                                                                                                       |
| `arg_max()`, `arg_min()`                               |  `arg_max()`  devuelve la fila que maximiza la expresión indicada. | `join`                                                 | `join` combina filas de dos tablas cuando coincide la clave. Si la columna tiene el mismo nombre en ambas: `on Clave`. | `union`                                                | `union` apila filas de varias tablas. `kind=outer` conserva todas las columnas; `kind=inner`, solo las compartidas. `withsource=Tabla` añade una columna con el nombre de la tabla de origen.                                                                                                                                                                                                                                                         |
| `let`                                                  | `let` asigna un nombre a un valor, consulta o función para reutilizarlo; cada declaración termina en `;`                                                                                                                                                                                                                                                                                                                                              |
| `extract()`                                            | `extract()` extrae de un texto una coincidencia de regex: `0` devuelve toda la coincidencia; `1`, el primer grupo entre paréntesis. | `parse`                                                | `parse` divide una columna de texto en otras según un patrón. `simple` exige coincidencias estrictas; `regex` permite delimitadores regex; `relaxed` devuelve `null` si falla la conversión de tipo. `parse-where` también elimina las filas que no coinciden.                                                                                                                                                                                        |
| `parse_json()`                                         | `parse_json()` convierte una cadena JSON en un valor `dynamic`; `todynamic()` es un alias. | `has` / `contains`                                     | `has` busca un término completo; `contains`, una subcadena. Ambos se aplican a una columna concreta. Usa `has` cuando puedas: suele ser más eficiente.                                                                                                                                                                                                                                                                                                |

- `kind` indica el tipo de `join`: define qué filas devuelve y si deduplica.
	- `kind=inner` devuelve todas las combinaciones que coinciden. Si el lado izquierdo tiene dos filas con la misma clave y ambas coinciden, devuelve ambas.
	- `kind=innerunique` (predeterminado) deduplica el lado izquierdo por la clave antes de unirlo; puede descartar filas repetidas de ese lado. No deduplica ambas tablas.
		- Ejemplo: si la izquierda tiene dos filas con `Id=1` y la derecha una, `inner` devuelve dos coincidencias; `innerunique`, una.
	- `leftouter`: conserva todo el lado izquierdo y añade lo que coincida; lo no coincidente queda a null. `rightouter` hace lo mismo desde la derecha y `fullouter` desde los dos lados.
	- `leftanti`: filas del lado izquierdo sin coincidencia, con las columnas de la izquierda; sirve para buscar ausencias. `anti` y `leftantisemi` son alias, y `rightanti` es su espejo.
	- `leftsemi`: filas del lado izquierdo que sí coinciden, también solo con las columnas de la izquierda. `rightsemi` es su espejo

> | join kind=leftanti (B) on Id

Reglas de examen:

1. Filtrar el tiempo en cada tabla antes del `join`.
2. Proyectar solo las columnas necesarias.
3. En un `join`, conservar los lados que exige el resultado y el `kind` elegido; si intercambiar las entradas conserva la semántica, colocar a la izquierda la tabla con menos filas después de filtrar.
4. Normalizar claves de texto con `tolower()` cuando corresponda.
5. Acotar correlaciones por tiempo: compartir una cuenta o IP no demuestra que dos eventos pertenezcan a la misma actividad.
6. Para tablas de inventario, usar `arg_max()` si se necesita el estado más reciente.
7. El orden respecto a `summarize` cambia el significado: `summarize arg_max(TimeGenerated, *) by Account` seguido de `| where EventID == 4624` da las cuentas cuya última actividad fue un inicio de sesión; filtrar primero y resumir después da el último inicio de sesión de cada cuenta que se haya conectado alguna vez.

### Visualizar con render

`render` va siempre como último operador y sobre una única salida tabular. No modifica el dato: le dice a la superficie de consulta cómo dibujarlo, así que antes se prepara el resultado con `where`, `summarize`, `bin()` o `top` y se quitan las columnas que sobran para que acierte con los ejes.

| Qué quieres mostrar | Gráfico |
| --- | --- |
| La evolución en el tiempo | `timechart`, con la columna del eje X de tipo `datetime` |
| Recuentos por categoría en barras verticales | `columnchart` |
| Lo mismo en barras horizontales | `barchart` |
| El reparto proporcional entre categorías | `piechart` |
| La relación entre dos medidas numéricas | `scatterchart` |
| La evolución rellenando el área bajo la serie | `areachart` |

Sin `render`, el resultado sale como `table`, que es el valor por defecto.

### Funciones guardadas y parsers ASIM

- Función guardada: guarda una consulta reutilizable; no almacena datos, se escribe en `Logs`, `Save` > `Save as function`
- `Advanced Security Information Model (ASIM)`: normaliza datos de distintos orígenes a esquemas comunes para reutilizar consultas y reglas.
- Parser unificador: reúne varias fuentes; parser específico: procesa una fuente concreta.
- Normalización en consulta: transforma al consultar, conserva los datos originales.
- Normalización en ingesta: transforma antes de almacenar.
- En Sentinel, prefiere `_Im_` y usa sus parámetros de filtro, como `starttime` y `endtime`.

## 6 · Patrones de consulta que debes comprender

### Alerta con sus evidencias

```kql
let alertas =
    AlertInfo
    | where Timestamp > ago(7d)
    | project AlertTime = Timestamp, AlertId, Title, Severity, ServiceSource;
let evidencias =
    AlertEvidence
    | where Timestamp > ago(7d)
    | project AlertId, EntityType, EvidenceRole, DeviceId, AccountUpn,
              RemoteIP, FileName;
alertas
| join kind=inner evidencias on AlertId
| sort by AlertTime desc
```

- `let alertas`: guarda alertas de los últimos 7 días y selecciona hora, ID, título, severidad y servicio.
- `let evidencias`: guarda evidencias de los últimos 7 días y selecciona el `AlertId` y datos de la entidad asociada.
- `join kind=inner ... on AlertId`: combina cada alerta con sus evidencias coincidentes; las alertas sin evidencia coincidente no aparecen. Una alerta con varias evidencias produce varias filas.
- `sort by AlertTime desc`: ordena los resultados del más reciente al más antiguo.

### Password spray en los inicios de sesión del workspace

```kql
SigninLogs
| where TimeGenerated > ago(24h)
| where ResultType == "50126"  // credenciales no válidas
| summarize Cuentas = dcount(UserPrincipalName), Intentos = count()
    by IPAddress, Ventana = bin(TimeGenerated, 15m)
| where Cuentas >= 5
| sort by Cuentas desc
```

### Del clic permitido al proceso iniciado después

`UrlClickEvents` aporta los clics permitidos de `Safe Links` con `ActionType == "ClickAllowed"`; `DeviceProcessEvents` aporta los procesos, dispositivos y líneas de comandos. La unión por `AccountUpn` y el intervalo de `10m` identifica una asociación temporal, no demuestra causalidad.

`periodo = 7d` selecciona una semana; cambiarlo a `30d` conserva la variante mensual de la consulta.

```kql
let periodo = 7d;
let clics =
    UrlClickEvents
    | where Timestamp > ago(periodo) and ActionType == "ClickAllowed"
    | project ClicEn = Timestamp, AccountUpn, Url;
clics
| join kind=inner (
    DeviceProcessEvents
    | where Timestamp > ago(periodo)
    | project ProcesoEn = Timestamp, DeviceName, AccountUpn, FileName, ProcessCommandLine
) on AccountUpn
| where ProcesoEn between (ClicEn .. ClicEn + 10m)
| project ClicEn, ProcesoEn, AccountUpn, Url, DeviceName, FileName, ProcessCommandLine
```

### Estado más reciente de cada dispositivo

```kql
DeviceInfo
| where Timestamp > ago(7d)
| summarize arg_max(Timestamp, *) by DeviceId
| project Timestamp, DeviceId, DeviceName, OSPlatform, OnboardingStatus
```

### Eventos ASR en Audit

`DeviceEvents` registra los eventos de `Attack Surface Reduction (ASR)`; este patrón selecciona las acciones cuyo nombre comienza por `Asr` y termina en `Audited`. 

```kql
DeviceEvents
| where ActionType startswith "Asr"
| where ActionType endswith "Audited"
```
