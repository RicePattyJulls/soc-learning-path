# SP-R11-L02 — REST API para búsquedas

**Región:** SP-R11 · **Producto:** Splunk Enterprise/Cloud (donde se indique) o SOAR Cloud explícito. · **Estado:** borrador documental / requiere revisión humana. · **SPL/CLI/API:** ilustrativo, NO ejecutado.

**Resultado curricular:** Identificar búsqueda, job SID, results y permisos

**Prerrequisitos:** R07, R09 (conceptual), R10

## 1. Explicación razonada

La API REST de Splunk identifica cada trabajo de búsqueda por un **SID**. La referencia Enterprise 10.2 documenta creación con `POST /services/search/jobs`, consulta de estado con `GET /services/search/jobs/{sid}` y recuperación de resultados con `GET /services/search/v2/jobs/{sid}/results`. La versión se elige por endpoint, no sustituyendo globalmente un prefijo. Crear un job cambia el estado del servicio, aunque su SPL solo lea datos. Esta distinción no autoriza conexiones ni operaciones desde el curso.

Diseña un cliente con SPL permitida, ventana e índices acotados, HTTPS verificado, rol mínimo, timeouts, presupuesto de jobs y trazabilidad. `count=0` permite pedir todos los resultados; la política didáctica exige 1–100. Algunos endpoints de resultados antiguos están obsoletos, pero creación y estado conservan las rutas anteriores en la referencia citada. Confirmar soporte Cloud y versión instalada antes de cualquier cliente real. Consulta [D10], sin asumir disponibilidad local.

Los ejemplos de este bloque son URLs informativas con `example.test`, no solicitudes ejecutables; no se incluyen credenciales ni instrucciones para desactivar seguridad. Un SID no equivale a autorización para explorar resultados de otra cuenta.

## 2. Conceptos clave

1. SID identifica job, no permiso global
2. POST creación de job ≠ modificación de datos indexados
3. Consultar resultados requiere RBAC y límite count/ventana
4. Versiones API v2 deben validarse por producto
5. HTTPS verificado y tokens acotados obligatorios

## 3. Procedimiento de estudio y verificación

1. Especifica una consulta SPL preaprobada con campos/índices permitidos.
2. Diseña petición conceptual de creación job y recepción SID, sin ejecutarla.
3. Define GET de estado y resultados con count máximo y expiración.
4. Incluye autenticación, TLS, roles y límites de concurrencia.
5. Define que 401/403, job caducado y timeout no deben disparar acciones mutantes.

**Alcance:** los nombres `IDX_*`, `ST_*`, dominios `example.test`, IDs y métricas de CSV son didácticos; no corresponden a una instancia verificada. Comandos de lectura solo se usarían en entorno autorizado; el paquete no los ejecuta.

## 5. Situación profesional

Un cliente recibe un SID. Debe distinguir estado (`/services/search/jobs/{sid}`) de resultados (`/services/search/v2/jobs/{sid}/results`) según [D10]; no migrar automáticamente ambos al mismo prefijo. Son rutas documentales, sin llamadas ejecutadas.

## 6. Errores comunes

1. Confundir SID con token de autenticación
2. Usar `count=0` sin límites y descargar resultados ilimitados
3. Definir «solo lectura» por verbo HTTP ignorando efectos de SPL


**Contrato de fixture:** [Columnas, mapeos y UTC](../VALIDACION/DATASETS.json). Los periodos relativos de ejemplos generales son estructurales; solo atribuir cifras a un CSV con su rango, población y snapshot explícitos. El modelo offline no configura Splunk ni recrea _indextime.

## 7. Actividades

### SP-R11-L02-Q01 — Opción múltiple

¿Qué representa un SID en la API de búsquedas?

A. Un permiso para leer resultados de cualquier usuario de la instancia
B. Un identificador de índice independiente del trabajo de búsqueda
C. El identificador de un trabajo de búsqueda, que no otorga por sí mismo permiso para leer sus resultados
D. Un token de ingesta que autoriza también búsquedas

### SP-R11-L02-Q02 — Opción múltiple

¿Qué práctica disminuye el riesgo de extracción masiva?

A. Usar solo TLS, manteniendo un rol administrativo y count=0
B. Limitar la salida visible del dashboard pero descargar todos los resultados
C. Acotar el tiempo pero permitir cualquier índice y volumen de resultados
D. Acotar resultados, tiempo e índices mediante un rol mínimo y un límite de extracción definido

### SP-R11-L02-P01 — Práctica abierta formativa

Especifica contrato conceptual de cliente de búsqueda: entradas permitidas, salida, errores, seguridad y auditoría.

## 8. Solucionario con razonamiento

- **SP-R11-L02-Q01: C** — SID refiere al trabajo creado, no concede permisos por sí solo.

- **SP-R11-L02-Q02: D** — Los límites y RBAC restringen volumen y alcance.

- **SP-R11-L02-P01:** Contrato documental Enterprise 10.2: POST /services/search/jobs crea SID; GET /services/search/jobs/{sid} consulta estado; GET /services/search/v2/jobs/{sid}/results recupera resultados. Exigir consultas y parámetros permitidos, earliest/latest, count entre 1 y 100, rol mínimo, HTTPS verificado, ownership y límites de jobs. Job expirado y 401/403 no disparan efectos externos. Sin llamadas REST; soporte de versión/Cloud pendiente.

**Guía de retroalimentación formativa:** Define fuente, producto, versión y límites del contexto; Resuelve el objetivo con un procedimiento replicable y no destructivo; Identifica error, caso benigno y riesgo operacional; Documenta permisos, aprobación y evidencia para revisión humana.

**Política educativa aprobada:** teoría autocorregible con umbral del 80 %; práctica abierta formativa, sin calificación automática ni premio de dominio práctico. Aprobar teoría no acredita dominio práctico de Splunk. La revisión humana independiente del contenido y la ejecución real siguen pendientes.
