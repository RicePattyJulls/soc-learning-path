# SP-R11-L03 — Webhooks y alert actions

**Región:** SP-R11 · **Producto:** Splunk Enterprise/Cloud (donde se indique) o SOAR Cloud explícito. · **Estado:** borrador documental / requiere revisión humana. · **SPL/CLI/API:** ilustrativo, NO ejecutado.

**Resultado curricular:** Reconocer integraciones y riesgos de datos

**Prerrequisitos:** R07, R09 (conceptual), R10

## 1. Explicación razonada

Una alerta puede comunicar resultados mediante webhook o una alert action específica. La salida contiene potencialmente IPs, identificadores, nombres de host, reglas y fragmentos del evento: todos pueden ser información sensible. Una integración de notificación debería transmitir **el mínimo contexto necesario** (ID de alerta, severidad orientativa, timestamp, enlace interno autenticado) y no eventos completos por defecto. El receptor debe ser un destino autorizado y estable, con validación TLS y controles contra solicitudes a endpoints arbitrarios.

Para resistir reintentos y alertas duplicadas, diseña `alert_id`, `event_window`, `delivery_id`, política de reenvío, máximo de intentos y registro sin secretos. La capacidad real de personalizar body/headers, firmar solicitudes o usar autenticación depende de la alert action/plugin/gateway concretos: no presupongas que el webhook genérico de Splunk genera HMAC nativa. Puedes proponer un gateway de confianza que autentique y minimice el payload antes de enviarlo a herramientas externas.

Una notificación que falla debe generar observabilidad, no activar una respuesta «más agresiva». El envío de datos fuera del perímetro demanda revisión de privacidad, acceso y retención antes del despliegue.

## 2. Conceptos clave

1. Datos de alerta pueden ser PII y secretos operativos
2. Webhook necesita destino aprobado y TLS válido
3. Dedupe delivery_id + retries acotados
4. Capacidad de HMAC depende de gateway/app concreta
5. Fallo de notificación no autoriza contención

## 3. Procedimiento de estudio y verificación

1. Enumera campos realmente necesarios para triage.
2. Clasifica receptores internos/externos y base de autorización.
3. Diseña envelope con IDs no sensibles y enlace autenticado.
4. Establece reintentos acotados, observabilidad y dedupe.
5. Define respuesta al error sin escalar privilegios.

## 4. Payload esquemático de demostración

```text
{
  "alert_id": "AL-EXAMPLE-01",
  "severity": "medium",
  "source": "auth_synthetic",
  "event_window_utc": "2026-10-16T14:00:00Z/2026-10-16T14:15:00Z",
  "link": "https://soc.example.test/incidents/AL-EXAMPLE-01"
}
```

**Alcance:** los nombres `IDX_*`, `ST_*`, dominios `example.test`, IDs y métricas de CSV son didácticos; no corresponden a una instancia verificada. Comandos de lectura solo se usarían en entorno autorizado; el paquete no los ejecuta.

## 5. Situación profesional

Un webhook está enviando `_raw` de Windows con usuario, IP y payload al servicio externo de tickets. Rediseña para enviar un identificador e investigación mediante enlace interno.

## 6. Errores comunes

1. Enviar `_raw` completo sin clasificación
2. Asumir firma HMAC en la acción básica sin documentación
3. Reintentos infinitos sin idempotencia


**Contrato de fixture:** [Columnas, mapeos y UTC](../VALIDACION/DATASETS.json). Los periodos relativos de ejemplos generales son estructurales; solo atribuir cifras a un CSV con su rango, población y snapshot explícitos. El modelo offline no configura Splunk ni recrea _indextime.

## 7. Actividades

### SP-R11-L03-Q01 — Opción múltiple

¿Cuál es un payload preferible para notificación externa?

A. La primera fila completa del resultado sin clasificación de datos
B. _raw de todos los resultados para que el receptor decida qué conservar
C. Un extracto de eventos con tokens operativos para facilitar el diagnóstico
D. Un identificador y contexto mínimo con enlace autenticado, evitando trasladar eventos crudos o secretos

### SP-R11-L03-Q02 — Opción múltiple

¿Cuál es un error de diseño habitual de webhook?

A. Registrar los IDs de entrega y limitar el número de reintentos
B. Dar por hecho que todo webhook nativo firma con HMAC
C. Tratar el body nativo como un esquema que requiere comprobarse por versión
D. Diseñar un gateway explícito para minimizar los datos enviados

### SP-R11-L03-P01 — Práctica abierta formativa

Define payload y política de envío para una notificación SOC. Incluye PII, TLS y manejo de duplicados.

## 8. Solucionario con razonamiento

- **SP-R11-L03-Q01: D** — Minimizar datos reduce superficie de exposición.

- **SP-R11-L03-Q02: B** — La firma depende del mecanismo implementado y debe verificarse.

- **SP-R11-L03-P01:** Enviar IDs/severidad/ventana y enlace interno, no raw logs; destino allowlisted, credenciales en secret manager, dedupe id, retries/backoff y auditoría sin secretos.

**Guía de retroalimentación formativa:** Define fuente, producto, versión y límites del contexto; Resuelve el objetivo con un procedimiento replicable y no destructivo; Identifica error, caso benigno y riesgo operacional; Documenta permisos, aprobación y evidencia para revisión humana.

**Política educativa aprobada:** teoría autocorregible con umbral del 80 %; práctica abierta formativa, sin calificación automática ni premio de dominio práctico. Aprobar teoría no acredita dominio práctico de Splunk. La revisión humana independiente del contenido y la ejecución real siguen pendientes.
