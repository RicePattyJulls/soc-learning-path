# SP-R10-L07 — Topologías, HA y clusters

**Región:** SP-R10 · **Producto:** Splunk Enterprise/Cloud (donde se indique) o SOAR Cloud explícito. · **Estado:** borrador documental / requiere revisión humana. · **SPL/CLI/API:** ilustrativo, NO ejecutado.

**Resultado curricular:** Distinguir search head cluster, indexer cluster, deploy server

**Prerrequisitos:** R01–R05; revisar R06–R07 para impacto SOC

## 1. Explicación razonada

Los roles de una arquitectura Splunk responden a funciones distintas. Un forwarder recoge/envía datos; indexers procesan y almacenan índices; search heads planifican y ejecutan búsquedas sobre search peers. Un **indexer cluster** gestiona disponibilidad de copias de buckets e indexación según factor de replicación y búsqueda; el nodo gestor coordina pero no elimina la necesidad de capacidad y topología correcta. Un **search head cluster** aporta escalado/HA de capa de búsqueda; requiere members compatibles y un deployer para ciertas configuraciones.

El **deployment server** no sustituye al deployer de search head cluster ni al cluster manager. Confundirlos ocasiona diagramas imposibles de operar. Para alta disponibilidad real hay que incluir fallos de zona, DNS, balanceadores, capacidad en picos, monitorización, backups y RPO/RTO; la mera presencia de tres máquinas no garantiza resiliencia. La documentación para Splunk Enterprise 10.2 exige al menos tres miembros para una topología de search head cluster destinada a HA de búsqueda, bajo sus otros requisitos.

La decisión de arquitectura depende de presupuesto y criticidad. Una instancia aislada puede ser apropiada para aprendizaje, pero no tiene tolerancia a la pérdida del host. En Splunk Cloud varias responsabilidades cambian de proveedor; no trasplantes instrucciones de administración del filesystem Enterprise como si el cliente Cloud tuviera acceso al mismo.

## 2. Conceptos clave

1. Indexer cluster != search head cluster
2. Deployer SHC != deployment server != cluster manager
3. RF/SF, capacidad y localización son parámetros de diseño
4. HA requiere RTO/RPO y pruebas de fallo, no solo un dibujo
5. Cloud vs Enterprise administrado localmente difieren

## 3. Procedimiento de estudio y verificación

1. Dibuja cadena input → forwarder → indexers → search heads.
2. Especifica quién administra cada configuración y app.
3. Elige requisitos HA, número de nodos y dominios de fallo.
4. Compara alternativas standalone y cluster con costes/operación.
5. Describe pruebas de recuperación sin ejecutar cambios.

## 4. Diagrama lógico documental

```text
Fuentes → Forwarders → Indexers (cluster opcional) ← Search Head(s)
                          ↑ manager                ↑ SHC deployer (si cluster)
Deployment server → forwarders gestionados (no sustituye los roles anteriores)
```

## 8. Solucionario con razonamiento

- **SP-R10-L07-Q01: D** — El SHC utiliza un deployer para coordinar el despliegue de determinados contenidos.

- **SP-R10-L07-Q02: C** — La documentación cita tres miembros como mínimo para disponibilidad de búsqueda.

- **SP-R10-L07-P01:** Pyme: standalone y backup explícito; SOC HA: indexers/search heads escalados con RF/SF, SHC miembros adecuados, cluster manager y deployer diferenciados, costes y RTO/RPO con pruebas futuras.
